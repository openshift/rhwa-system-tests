## 2. Summary

A node fenced by SBR against a Ceph RBD block device must stay fenced exactly
once: after the fence reboots the node and the `StorageBasedRemediation` CR is
deleted, the node returns Ready and schedulable, the agent restarts, and the
operator does not create a second remediation CR for that node. The test proves
that the fencing state recorded on Block-mode shared storage is read back
correctly after the reboot, rather than being re-interpreted as a new fence
request ("phantom re-fencing").

## 3. Scope

- **In scope**: an SBRC configured with `sharedStorageVolumeMode: Block` on a
  Ceph RBD StorageClass; a manually created `StorageBasedRemediation` CR
  reaching `FencingSucceeded=True`; the target node rebooting (boot-id change)
  and returning Ready; the out-of-service taint clearing after the CR is
  deleted; the SBR agent pod returning to Running/ContainersReady on the
  rebooted node; no new `StorageBasedRemediation` CR appearing for that node.
- **Out of scope**:
  - **The RBD slot contents themselves.** The two "block device slot state"
    steps do not read the device. `block_storage_rbd.go:386` and `:411` assign
    fixed strings and log them; the comment at `:383-385` describes the exec
    into the agent pod that a real capture would need. Persistence is inferred
    from the absence of a new remediation CR, not from a before/after slot
    comparison.
  - **Sustained absence of re-fencing.** The final step uses `Eventually`, which
    passes on the first `IsNotFound`; it does not hold the condition over time.
    A `Consistently` would be needed to prove no CR appears later.
  - **The NHC-triggered path.** The spec creates no `NodeHealthCheck` CR and
    runs standalone against SBR. NHC-driven SBR remediation is covered by
    `nhc_integration.go`.
  - **CephFS / Filesystem-mode fencing**, covered by `storage_loss_watchdog.go`
    and `storage_loss_write_only.go`; **watchdog behaviour**, covered by
    `detect_only.go`.

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator
export ECO_TEST_LABELS='operator:sbr && tier:acceptance'
export SBR_RBD_STORAGE_CLASS=ocs-storagecluster-ceph-rbd   # optional
```

`SBR_RBD_STORAGE_CLASS` names the Ceph RBD StorageClass to use. Unset is the
normal case: the test auto-discovers the first StorageClass whose provisioner
contains `rbd.csi.ceph.com`, and `Skip`s with "No Ceph RBD StorageClass found;
install ODF or set SBR_RBD_STORAGE_CLASS env var" when there is none. This is a
separate variable from the suite's `SBR_STORAGE_CLASS`, which selects an RWX
CephFS class and is not read here.

## 5. Preconditions

1. SBR operator installed in `openshift-workload-availability` with its
   controller running.
2. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one;
   otherwise the suite skips.
3. `StorageBasedRemediationConfig/test-sbrc-block-persistent-fencing` is created
   with that class and `sharedStorageVolumeMode: Block`, and its agent DaemonSet
   reaches full readiness (`waitForSBRCReady`, `sbrparams.SBRCReadyTimeout`).
4. The installed SBR operand supports block-mode shared storage
   (`requireSBRCBlockVolumeModeSupport`): the SBRC CRD's served spec schema
   includes `sharedStorageVolumeMode`. A missing field fails the precondition;
   the check reads the API directly because WAO owns the CRD and CSV.
5. A schedulable worker node that hosts no SBR controller pod is available;
   `BeforeAll` skips the suite when `pickTargetWorkerNode` finds none.

`BeforeAll` creates the SBRC without tolerating `AlreadyExists`, so a leftover
SBRC of the same name from an aborted run fails the suite rather than being
cleaned and recreated — see section 8.

## 6. Test steps

| #   | Step (`By` text)                                                      | Expected result                                                                                                                                  |
| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `Recording boot-id for node <node> before fencing`                    | `status.nodeInfo.bootID` is read and non-empty                                                                                                   |
| 2   | `Creating StorageBasedRemediation CR to trigger fencing`              | CR named after the target node is admitted in the operator namespace                                                                             |
| 3   | `Waiting for FencingSucceeded=True on the StorageBasedRemediation CR` | `FencingSucceeded=True` within `sbrparams.SBRCRCleanupTimeout` (10m); the CR vanishing before the condition is seen fails the step               |
| 4   | `Capturing block device slot state before node reboot`                | An agent pod (`app=sbr-agent`) is found on the target node. No device state is read — see section 3                                              |
| 5   | `Waiting for node <node> to reboot`                                   | boot-id differs from step 1 within `sbrparams.NodeRebootTimeout` (20m)                                                                           |
| 6   | `Waiting for node <node> to become Ready after reboot`                | `Ready=True` within `sbrparams.NodeRebootTimeout`                                                                                                |
| 7   | `Deleting StorageBasedRemediation CR to trigger taint removal`        | CR deleted, or already gone, within `medik8sparams.DefaultTimeout`                                                                               |
| 8   | `Waiting for out-of-service taint to be removed`                      | Node is schedulable again (no blocking taint, not cordoned) within `sbrparams.NodeRebootTimeout`; boot-id is then asserted to differ from step 1 |
| 9   | `Waiting for agent pod to restart on rebooted node`                   | An agent pod on the node is `Running` with `ContainersReady=True` within `sbrparams.BlockFencingStateCheckTimeout` (5m)                          |
| 10  | `Capturing block device slot state after reboot`                      | Placeholder string logged; no device inspected — see section 3                                                                                   |
| 11  | `Verifying no duplicate fencing attempts occurred`                    | No `StorageBasedRemediation` CR exists for the node (`IsNotFound`)                                                                               |

A background goroutine logs the node's Ready condition, boot-id, and taints
every 30s from step 2 until the spec ends; it is diagnostic only and asserts
nothing.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1916")` runs and passes.
- `StorageBasedRemediation/<node>` reaches `FencingSucceeded=True` within
  `sbrparams.SBRCRCleanupTimeout`.
- The node's boot-id after the fence differs from the boot-id recorded in step
  1, and the node reports `Ready=True`.
- After the CR is deleted the node is schedulable again — no out-of-service
  taint, not cordoned.
- An SBR agent pod is `Running` with `ContainersReady=True` on the rebooted node
  within `sbrparams.BlockFencingStateCheckTimeout`.
- No `StorageBasedRemediation` CR exists for the node after the reboot.
- Cleanup finishes: the SBRC and any remediation CR for the node
  are gone, and the node is left Ready, uncordoned, and schedulable.

## 8. Failure / known issues

No open product bug gates this spec, so it carries no env var skip-gate.

| Issue                                                                                                                                                          | Effect on this test                                                                                                       | Handling                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The out-of-service taint evicts the Ceph CSI nodeplugin from the fenced node                                                                                   | While the taint is on the target node, PVC mounts there hang in `ContainerCreating`                                       | The test schedules no PVC-backed workload on the target node, and steps 7-8 clear the taint before step 9                                                                  |
| [DFBUGS-11731](https://redhat.atlassian.net/browse/DFBUGS-11731): csi-addons deletes the CSIAddonsNode during node reboot, so ceph-csi auto-unfence never runs | Step 9's 5m window can be exceeded while the RBD CSI nodeplugin re-registers on the rebooted node (observed 32s to 4m10s) | Not gated. The spec runs standalone (no `NodeHealthCheck` CR), so a stale `SBRStorageUnhealthy` condition cannot trigger re-fencing during recovery; the deadline stays 5m |
| Stale SBRC from an aborted run                                                                                                                                 | `BeforeAll` creates `test-sbrc-block-persistent-fencing` without tolerating `AlreadyExists`, so the suite fails           | Delete the leftover SBRC before re-running                                                                                                                                 |

Test-side gaps, tracked against this ticket rather than a product bug:

- `reportxml.ID` in the spec is the literal string `TBD`; it must be `1916`
  before this document moves to `implemented`.
- The block device slot capture is stubbed (section 3). Until it reads the
  device, the title's "persistent fencing state" is evidenced only by the
  absence of a second remediation CR.

## 9. Cleanup

- `DeferCleanup` force-removes the `StorageBasedRemediation` CR for the target
  node — `cleanupSBRCR` clears finalizers first — and cancels the node-status
  logging goroutine.
- `AfterAll` deletes the SBRC and waits for it to be fully gone, force-deletes
  any leftover remediation CR for the node, and uncordons the node when it is
  still unschedulable. Each step tolerates `IsNotFound`. The order matters: the
  SBRC is deleted first, so a remediation CR still present at that point has no
  controller left to clear its finalizer, and the force-delete is what keeps it
  from stranding.
- Recovery runs even when the spec failed mid-way: a failure between the fence
  and the CR deletion leaves the node tainted, and `AfterAll` is what returns it
  to schedulable. Uncordon failures are logged with `GinkgoWriter.Printf`
  instead of failing the suite.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="operator:sbr && tier:acceptance" \
    --focus="fencing state persists on Ceph RBD" ./tests/sbr-operator
```

In a second terminal, record the victim's boot ID and watch the remediation:

```bash
watch -n 5 -d tools/watch/sbr-watch.sh
# Without watch: tools/watch/sbr-watch.sh --loop
```

The victim must return with a changed boot ID; the controller and witness nodes
must remain Ready. This spec deletes its completed SBR CR during cleanup.
