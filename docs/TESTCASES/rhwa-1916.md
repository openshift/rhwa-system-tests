# RHWA-1916 — SBR fencing state survives the fenced node's reboot on Ceph RBD block storage

## 2. Summary

A node fenced by SBR against a Ceph RBD block device must stay fenced exactly
once: after the fence reboots the node and the `StorageBasedRemediation` CR is
deleted, the node returns Ready and schedulable, the agent restarts, and the
operator does not create a second remediation CR for that node. The test proves
that the fencing state recorded on Block-mode shared storage is read back
correctly after the reboot, rather than being re-interpreted as a new fence
request ("phantom re-fencing").

## 3. Scope

- **In scope**: an SBRC configured with `sharedStorageVolumeMode: Block` on a
  Ceph RBD StorageClass; a manually created `StorageBasedRemediation` CR
  reaching `FencingSucceeded=True`; a fence request visible in the target's
  on-device fence slot through an observer agent; the target node rebooting
  (boot-id change) and returning Ready; the out-of-service taint clearing after
  the CR is deleted; the SBR agent pod returning to Ready on the rebooted node;
  the fence slot becoming quiet (empty or `FENCE_REASON_NONE`) after the agent
  restarts; no new `StorageBasedRemediation` CR appearing for that node for
  `BlockNoFencingCheckDuration`.
- **Out of scope**:
  - **Fence slot geometry / off-by-one writes.** Covered by
    `block_storage_fence_geometry.go` (RHWA-2031). This spec only asserts that
    the target's own slot holds a fence before reboot and is quiet after recovery.
  - **The NHC-triggered path.** The spec creates no `NodeHealthCheck` CR and
    runs standalone against SBR. NHC-driven SBR remediation is covered by
    `nhc_integration.go` and `block_storage_node_hang.go`.
  - **CephFS / Filesystem-mode fencing**, covered by `storage_loss_watchdog.go`
    and `storage_loss_write_only.go`; **watchdog behaviour**, covered by
    `detect_only.go`.

## 4. Environment

| Requirement  | Value                                                                                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cluster      | OCP with at least two nodes running SBR agents (one victim that hosts no SBR controller, plus one observer) that may reboot the victim                        |
| Topology     | any (the spec sets no topology label)                                                                                                                         |
| Platform     | any (`platform:any`)                                                                                                                                          |
| Storage      | A Ceph RBD **block** StorageClass — ODF `openshift-storage.rbd.csi.ceph.com` or Rook `rook-ceph.rbd.csi.ceph.com`; used with `sharedStorageVolumeMode: Block` |
| Network      | connected or disconnected                                                                                                                                     |
| Namespace    | `openshift-workload-availability` (`medik8sparams.OperatorNs`)                                                                                                |
| Destructive? | yes — the target worker node is fenced and hard-rebooted, and carries the out-of-service taint until the CR is deleted                                        |

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator
export ECO_TEST_LABELS='operator:sbr && tier:acceptance'
export SBR_RBD_STORAGE_CLASS=ocs-storagecluster-ceph-rbd   # optional
```

`SBR_RBD_STORAGE_CLASS` names the Ceph RBD StorageClass to use. Unset is the
normal case: the test auto-discovers the first StorageClass whose provisioner
contains `rbd.csi.ceph.com`, and `Skip`s with "No Ceph RBD StorageClass found;
install ODF or set SBR_RBD_STORAGE_CLASS env var" when there is none. This is a
separate variable from the suite's `SBR_STORAGE_CLASS`, which selects an RWX
CephFS class and is not read here.

## 5. Preconditions

1. SBR operator installed in `openshift-workload-availability` with its
   controller running.
2. Self Node Remediation is not running (`failIfSNRRunning` inside
   `setupBlockModeSBRC`); SNR and SBR both claim `/dev/watchdog`.
3. No `NodeHealthCheck` remediates through the SBR template
   (`requireNoSBRNodeHealthCheck`); otherwise a second CR would break the
   exactly-once assertion.
4. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one;
   otherwise the suite skips.
5. The installed SBR operator supports block-mode shared storage
   (`requireSBRCBlockVolumeModeSupport`): the SBRC CRD's spec schema includes
   `sharedStorageVolumeMode`, or the installed CSV predates 5.8.0 (the first
   release shipping [RHWA-1313](https://redhat.atlassian.net/browse/RHWA-1313))
   and the suite `Skip`s with that reason. A CSV at or above 5.8.0 whose CRD
   lacks the field fails loudly instead.
6. `StorageBasedRemediationConfig/test-sbrc-block-persistent-fencing` is created
   (after a stale-SBRC pre-clean via `deleteSBRCAndWait`), reaches agent DaemonSet
   readiness, and reports `status.storageValidation.concurrentWriteable=true`.
7. A schedulable worker node that hosts no SBR controller pod is available, and
   another node runs an observer agent for that SBRC; `BeforeAll` skips when
   either is missing.

`BeforeAll` also clears residual Ceph OSD blocklist entries so a prior fencing
test cannot leave the shared volume unmappable (DFBUGS-11731).

## 6. Test steps

| #   | Step (`By` text)                                                                                         | Expected result                                                                                                                                          |
| --- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `Recording boot-id for node <node> before fencing`                                                       | `status.nodeInfo.bootID` is read and non-empty                                                                                                           |
| 2   | `Creating StorageBasedRemediation CR to trigger fencing`                                                 | CR named after the target node is admitted in the operator namespace                                                                                     |
| 3   | `Waiting for FencingSucceeded=True on the StorageBasedRemediation CR`                                    | `FencingSucceeded=True` within `sbrparams.SBRCRCleanupTimeout` (10m); the CR vanishing before the condition is seen fails the step                       |
| 4   | `Capturing block device fence slot state before node reboot`                                             | Through the observer agent, the target's fence slot holds a fence request targeting its node ID within `sbrparams.BlockFenceWriteTimeout`               |
| 5   | `Waiting for node <node> to reboot`                                                                      | boot-id differs from step 1 within `sbrparams.NodeRebootTimeout` (20m)                                                                                   |
| 6   | `Waiting for node <node> to become Ready after reboot`                                                   | `Ready=True` within `sbrparams.NodeRebootTimeout`                                                                                                        |
| 7   | `Deleting StorageBasedRemediation CR to trigger taint removal`                                           | CR deleted, or already gone, within `sbrparams.SBRCRCleanupTimeout`                                                                                      |
| 8   | `Waiting for out-of-service taint to be removed`                                                         | Node is uncordoned with no out-of-service taint (`nodeRestoredAfterRemediation`) within `sbrparams.NodeRebootTimeout`; boot-id differs from step 1       |
| 9   | `Clearing the Ceph OSD blocklist left on the target by the fencing`                                      | Best-effort `clearCephOSDBlocklist` so the rebooted node's RBD map is not blocked by DFBUGS-11731                                                        |
| 10  | `Waiting for agent pod to restart on rebooted node`                                                      | The SBRC's agent on the node reports Ready within `sbrparams.BlockAgentReadyAfterRebootTimeout` (10m)                                                    |
| 11  | `Capturing block device fence slot state after reboot`                                                   | Through the observer, the target's fence slot is quiet (empty or `FENCE_REASON_NONE`) within `sbrparams.BlockFencingStateCheckTimeout`                   |
| 12  | `Consistently asserting for <duration> that no duplicate fencing occurs (...)`                           | For `sbrparams.BlockNoFencingCheckDuration` (90s): boot-id stays at the post-reboot value, node stays Ready, no `StorageBasedRemediation` CR appears     |

A background goroutine logs the node's Ready condition, boot-id, and taints
every 30s from step 2 until the spec ends; it is diagnostic only and asserts
nothing.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1916")` runs and passes.
- `StorageBasedRemediation/<node>` reaches `FencingSucceeded=True` within
  `sbrparams.SBRCRCleanupTimeout`.
- Before the reboot, the target's on-device fence slot holds a fence request
  targeting its node ID.
- The node's boot-id after the fence differs from the boot-id recorded in step
  1, and the node reports `Ready=True`.
- After the CR is deleted the node is schedulable again — no out-of-service
  taint, not cordoned.
- The SBRC's agent pod on the rebooted node reports Ready within
  `sbrparams.BlockAgentReadyAfterRebootTimeout`.
- After the agent restarts, the target's fence slot is quiet (empty or
  `FENCE_REASON_NONE`), proving the on-device fencing state was read back and
  disarmed rather than left as a live fence request.
- For `BlockNoFencingCheckDuration` the node keeps its post-reboot boot-id,
  stays Ready, and has no `StorageBasedRemediation` CR (no phantom re-fencing).
- Cleanup finishes: the SBRC and any remediation CR for the node
  are gone, and the node is left Ready, uncordoned, and schedulable.

## 8. Failure / known issues

No open product bug gates this spec, so it carries no env var skip-gate.

| Issue                                                                                                                                                          | Effect on this test                                                                                                       | Handling                                                                                                                                                                   |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The out-of-service taint evicts the Ceph CSI nodeplugin from the fenced node                                                                                   | While the taint is on the target node, PVC mounts there hang in `ContainerCreating`                                       | Steps 7-8 clear the taint before step 10 waits for the agent                                                                                                               |
| [DFBUGS-11731](https://redhat.atlassian.net/browse/DFBUGS-11731): csi-addons deletes the CSIAddonsNode during node reboot, so ceph-csi auto-unfence never runs | After the taint is gone the RBD map can still fail (`ret=-108`) and the agent never becomes Ready                         | Step 9 calls `clearCephOSDBlocklist` before waiting for the agent; step 10 uses a 10m timeout for CSI remount                                                              |
| Stale SBRC from an aborted run                                                                                                                                 | Recreating on a Terminating shared PVC wedges device-init                                                                 | `setupBlockModeSBRC` pre-cleans with `deleteSBRCAndWait` before create                                                                                                     |

## 9. Cleanup

- `DeferCleanup` force-removes the `StorageBasedRemediation` CR for the target
  node — `cleanupSBRCR` clears finalizers first — and cancels the node-status
  logging goroutine.
- `AfterAll` clears residual Ceph OSD blocklist entries, force-deletes any
  leftover remediation CR for the node, deletes the SBRC via
  `deleteSBRCAndWait` (CR + DaemonSet + pods + Jobs + shared PVC), and uncordons
  the node when it is still unschedulable. Each step tolerates `IsNotFound`.
- Recovery runs even when the spec failed mid-way: a failure between the fence
  and the CR deletion leaves the node tainted, and `AfterAll` is what returns it
  to schedulable. Uncordon failures are logged with `GinkgoWriter.Printf`
  instead of failing the suite.
