## 2. Summary

### Implementation refinement

The implementation retains the original PVC until final cleanup. A test-owned
finalizer holds the deleting SBRC until the operator finishes its cleanup
finalizer. The test then removes only the old SBRC's owner reference from its
PVC and releases its own finalizer. It never removes an operator finalizer.
The read-only observer stays mounted on that PVC, and recreation must use the
same PVC UID and PV name. This replaces the PVC-disappearance steps below:
reusing a StorageClass alone does not guarantee reusing its data, and the
controller changes the PV reclaim policy to Delete.

Only test-owned resources are cleaned up, not all namespace cleanup Jobs.
The test proves map removal and healthy same-volume recreation. A pre-fix build
will fail the missing-cleanup-Job assertion, but reproducing the historical
restart loop is not guaranteed. RHWA-1058 remains out of scope.

Live cluster validation and a pre-fix comparison are still pending.

Deleting a `StorageBasedRemediationConfig` must wipe the node map file on the shared PVC
before the PVC goes away. Without that, recreating the SBRC against the same backing storage
leaves the new agents reading stale node IDs with ~105s-old heartbeats, the peer monitor flags
them as unhealthy, the liveness probe kills the pod, and agents restart-loop for ~10 minutes
before the entries age out.

## 3. Scope

- **In scope** — the RHWA-1056 half of PR #69:
  - On SBRC deletion the controller creates a cleanup job named `<sbrc>-sbr-cleanup-*` in the
    operator namespace, and that job reaches `Complete`.
  - The node map file is gone from the shared storage after the job runs.
  - The cleanup job completes **before** the PVC is removed — it mounts that PVC, so the
    ordering is what makes the fix work at all.
  - Recreating the SBRC with the same name and spec against the same StorageClass brings
    every agent to `1/1 Running` with **at most 1 restart per pod**, within the budget on the
    ticket, and the SBRC reaches `Ready`.
  - The agents log no peer-unhealthy event for a node ID that is not an active target during
    the convergence window.
- **Out of scope**:
  - **RHWA-1058 (ghost peer `nodeID=1`).** PR #69 fixes it in the same change
    (`clearPreflightSlot` in `cmd/sbr-agent/main.go`), but it is a different observable — a
    recurring `Skipping peer check - unable to resolve node name` with `peerNodeID: 1` on a
    *steady-state* cluster, with no delete/recreate involved. It deserves its own test case
    and its own ticket; a note goes in section 13 so it is not lost.
  - The unit-level behaviour PR #69 covers upstream: slot 1 cleared when the agent is assigned
    a different node ID, slot 1 preserved when the agent *is* node ID 1, node-manager locking
    during slot cleanup, and the cleanup-job timeout constants. These are in
    `cmd/sbr-agent/main_test.go` and need no cluster.
  - The `reclaimPolicy: Retain` → `Delete` PV patch in `handleDeletion`. It predates this PR
    and addresses Released-PV accumulation, a different symptom.
  - Block-mode (`sharedStorageVolumeMode: Block`) node maps. RHWA-1056 is about the
    filesystem node map file (`<mount>/sbr-device-nodemap`); the Block-mode on-device node map
    read by `readNodeMapFromPod` in `block_storage_inspection.go` (RHWA-1926) is a different
    structure on a different code path.
  - Fencing and remediation outcomes. Nothing is fenced here.

### Why the existing lifecycle test does not cover this

`sbrc_lifecycle.go` (OCP-88734) looks adjacent but does not reach the bug. Its sequence is
create **A** → patch A → delete A → create **B** → delete B. RHWA-1056 needs the *same* SBRC
name and spec recreated against the *same* backing storage, so that the hostname hash yields
the same node IDs and the new agents collide with the previous run's entries. Creating a
differently named B provisions a different PVC and sidesteps the collision entirely. OCP-88734
also asserts only on DaemonSet readiness and removal — never on pod restart counts, the node
map file, or the cleanup job.

Reproducing the bug ideally wants a StorageClass with `reclaimPolicy: Retain`, since that is
what preserves the backing export. The test does **not** require it: the assertions are on the
cleanup job running and the node map being gone, which hold under either reclaim policy, and
step 7's recreate re-binds the same StorageClass either way. A `Retain` class makes step 7 a
stronger reproduction; record which policy the run used in the report.

## 5. Preconditions

Asserted in `BeforeAll`:

1. The SBR operator deployment is Ready.
2. A filesystem-mode RWX StorageClass is discoverable or named by `SBR_STORAGE_CLASS`;
   otherwise skip. Its `reclaimPolicy` is recorded and attached to the report.
3. At least two schedulable worker nodes, so the node map holds more than one entry and a
   single-node false pass is impossible.
4. Self Node Remediation is not running — SNR and SBR both claim `/dev/watchdog`, as the
   other destructive SBR specs already require.
5. No `NodeHealthCheck` references a `StorageBasedRemediationTemplate`, so nothing fences a
   node while the agents are restarting.
6. Any SBRC from a previous run with this test's name is deleted and fully gone, including
   its finalizer drain and DaemonSet garbage collection, before the first create.
7. The operator namespace has no leftover `sbr-cleanup` jobs from a previous run; any found
   are deleted so step 3 cannot match a stale one.

| -- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1  | Creating the StorageBasedRemediationConfig and waiting for its agent DaemonSet to be ready        | All agent pods are `1/1 Running` within `sbrparams.SBRCReadyTimeout`; the applied spec is captured for re-use in step 7 |
| 2  | Recording the node map entries and the agent pod restart counts before deletion                   | The node map file exists on the shared PVC with one entry per agent node; baseline restart counts recorded |
| 3  | Deleting the StorageBasedRemediationConfig and waiting for the cleanup job to complete            | A job named `<sbrc>-sbr-cleanup-*` appears in the operator namespace and reaches `JobComplete=True` within `sbrparams.NodeMapCleanupJobTimeout` |
| 4  | Verifying the cleanup job ran before the PVC was removed                                          | The cleanup job's completion timestamp precedes the PVC's disappearance; the job's pod mounted the shared PVC |
| 5  | Waiting for every agent pod, the DaemonSet, the SBRC and the PVC to be fully gone                 | No agent pod for this SBRC remains — not even Terminating — and the DaemonSet, SBRC and PVC are all `IsNotFound` within `sbrparams.SBRCReadyTimeout` |
| 6  | Verifying the node map file no longer exists on the shared storage                                | A debug pod mounting the same StorageClass finds no `sbr-device-nodemap`; the cleanup job log reports either removal or that the file was already absent |
| 7  | Recreating the StorageBasedRemediationConfig with the name and spec captured in step 1            | The SBRC is admitted and a new agent DaemonSet is created; the recreate clock starts here       |
| 8  | Asserting every agent pod reaches Running and Ready with at most one restart                      | Within `sbrparams.NodeMapRecreateReadyTimeout`, every agent pod is `1/1 Running` and its `restartCount` is ≤ `sbrparams.NodeMapMaxAgentRestarts`; the elapsed time since step 7 is recorded with `AddReportEntry` — the assertion that fails on a pre-fix build |
| 9  | Consistently verifying no agent pod restarts during the convergence window                        | Across `sbrparams.NodeMapConvergenceDuration`, no agent pod's `restartCount` increases           |
| 10 | Verifying no agent logs a peer-unhealthy event for a node that is not an active target             | No `Peer node became unhealthy` entry naming a node ID absent from the current node map          |

Steps 8 and 9 are the regression signal. The ticket records the failure as "11 restarts on a
single node, ~10 minutes to stabilize" against an expectation of "0 or at most 1 restart"
within 1–2 minutes, so a restart-count ceiling is the assertion that distinguishes fixed from
broken. Step 9 exists because step 8 alone could pass by catching the pods during a lull
between restarts.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1929")` runs and passes.
- On deletion, a `<sbrc>-sbr-cleanup-*` job reaches `JobComplete=True` within
  `sbrparams.NodeMapCleanupJobTimeout`, and it completes before the shared PVC disappears.
- Every agent pod of the deleted SBRC is gone — none left Terminating — along with the
  DaemonSet, the SBRC and the PVC, before the recreate begins.
- After deletion the node map file does not exist on the shared storage.
- After recreating the SBRC with the same name and the spec captured in step 1, every agent
  pod reaches `1/1 Running` within `sbrparams.NodeMapRecreateReadyTimeout` with
  `restartCount` ≤ 1, and no restart count increases across
  `sbrparams.NodeMapConvergenceDuration`. The elapsed recreate time is attached to the report
  so drift against the ticket's 1–2 minute expectation stays visible.
- No agent logs `Peer node became unhealthy` for a node ID that is not in the current node map.
- The recreated SBRC reaches `Ready=True`.
- Cleanup finishes: the test SBRC, its DaemonSet, its PVC and any debug pod are gone, and no
  `sbr-cleanup` job is left behind beyond its own `TTLSecondsAfterFinished`.

On a build without PR #69 this spec fails at step 3 — no cleanup job is ever created, so the
`Eventually` times out — and would fail at step 8 even if the job check were relaxed.

## 8. Failure / known issues

| Issue | Effect | Gate |
| ----- | ------ | ---- |
| [RHWA-1056](https://redhat.atlassian.net/browse/RHWA-1056) is `ON_QA`, not `Closed`. | The fix is in the 5.0 build but not QA-verified. If absent from the build under test, step 3 times out. | Not gated. A clear timeout on a missing cleanup job is a better signal than a skip. |
| Cleanup failure is **non-fatal by design**: `handleDeletion` logs, emits a `Warning` event with recovery instructions, and continues deleting. | A cluster where the cleanup job cannot run still deletes the SBRC, so steps 5 and 7 pass while 3, 6 and 8 fail. | Not gated. Step 3 must assert the job reached `Complete`, not merely that deletion finished — otherwise the spec passes on exactly the broken path the fix added the event for. |
| `clearPreflightSlot` unconditionally zeroes slot 1, even when a node legitimately hashes to it (~1/256). | That node misses 1–2 heartbeats on startup. The code comments argue this is well inside the 7-missed-heartbeat tolerance. | Not gated here. Step 9's window is long enough that a transient slot-1 gap would not trip remediation, but if this spec ever flakes on a cluster whose node hashes to slot 1, this is the first thing to check. |

## 9. Cleanup

- `DeferCleanup` deletes the test SBRC (clearing finalizers if it is stuck), waits for the
  SBRC, DaemonSet and PVC to be fully gone, and tolerates `IsNotFound` throughout.
- `DeferCleanup` deletes the debug pod used in steps 2 and 6, and deletes a same-named
  leftover before creating it, so a killed run does not block the next one.
- `AfterAll` removes any `sbr-cleanup` job still present in the operator namespace. The
  controller sets `TTLSecondsAfterFinished: 300`, so these normally disappear on their own;
  the sweep exists so a failed run does not leave one to confuse the next run's step 3.
- Cleanup logs with `GinkgoWriter.Printf` rather than failing the suite on a missing resource.

## 12. Implementation sketch

```go
It("Verify SBRC deletion wipes the node map so recreation does not restart-loop agents",
    reportxml.ID("1929"),
    Label(
        labels.OperatorSBR,
        labels.TierAcceptance,
        labels.ComponentController,
        labels.DisruptionNonDestructive,
        labels.PlatformAny,
        labels.FrequencyNightly,
    ), func() {
        By("Creating the StorageBasedRemediationConfig and waiting for its agent DaemonSet to be ready")
        // ...

        By("Deleting the StorageBasedRemediationConfig and waiting for the cleanup job to complete")
        cleanupJob := awaitCleanupJobComplete(ctx, sbrcName)
        Expect(cleanupJob).ToNot(BeNil(),
            "Deleting SBRC %q must create a node map cleanup job (RHWA-1056)", sbrcName)

        By("Recreating the StorageBasedRemediationConfig with the same name and spec")
        // ...

        By("Asserting every agent pod reaches Running and Ready with at most one restart")
        Eventually(func() error {
            return agentsReadyWithinRestartBudget(ctx, sbrcName, sbrparams.NodeMapMaxAgentRestarts)
        }, sbrparams.NodeMapRecreateReadyTimeout,
            sbrparams.DefaultPollInterval).Should(Succeed(),
            "Agents must come back without a restart loop after SBRC recreation")

        By("Consistently verifying no agent pod restarts during the convergence window")
        // ...
    })
```

Reusable from the suite: `discoverRWXStorageClass`, `buildSBRC`, `sbrcAgentPods`,
`agentRestartCount`, `createHostCommandPod` / `runHostCommandPod` (for the PVC-mounting debug
pod in steps 2 and 6), `sbrparams.InjectorImage`, and the finalizer-drain deletion pattern
already in `sbrc_lifecycle.go`'s `BeforeAll`.

New constants for `tests/sbr-operator/internal/sbrparams/const.go`:

| Constant                         | Value | Why                                                                                           |
| -------------------------------- | ----- | ------------------------------------------------------------------------------------------------ |
| `SBRCNodeMapTestName`            | `"test-sbrc-node-map"` | A dedicated name, reused verbatim across delete and recreate — using the same name is the point. |
| `NodeMapCleanupJobLabelSelector` | `"app.kubernetes.io/component=sbr-cleanup"` | The controller labels the job with this; matching on it is more robust than the `GenerateName` prefix. |
| `NodeMapCleanupJobTimeout`       | `6m`  | The controller polls for `CleanupJobPollTimeout` (240s) with `ActiveDeadlineSeconds` 300s, so the test must outlast the controller's own deadline plus image pull. |
| `NodeMapRecreateReadyTimeout`    | `3m`  | The ticket says 1–2 minutes. The agent image is already cached on every node from step 1, so the recreate does not pay an image pull and the ticket's budget is realistic; 3m is modest CI headroom. It must stay well under the ~10 minutes a pre-fix build takes to converge — that gap is the whole assertion. The measured value is attached to the report. |
| `NodeMapConvergenceDuration`     | `3m`  | Longer than the ~105s peer timeout on the ticket, so a stale entry that was going to trip the peer monitor would have done so. |
| `NodeMapMaxAgentRestarts`        | `1`   | The ticket's "0 or at most 1 restart (image pull + normal startup)".                            |
| `NodeMapFileSuffix`              | `"-nodemap"` | Appended to the SBR device file name; the full path is `<mount>/sbr-device-nodemap`.      |
| `PeerUnhealthyMessage`           | `"Peer node became unhealthy"` | The agent log line asserted in step 10.                                       |

`NodeMapRecreateReadyTimeout` is the value most worth confirming on a real cluster before
this moves off `draft`: it has to sit above a healthy recreate and below the pre-fix
convergence time, and both ends are cluster-speed dependent.
