This is the Block-mode counterpart of the Filesystem node hang test
(`tests/sbr-operator/tests/node_hang.go`, OCP-88738). It carries its own
`reportxml.ID("1931")` rather than sharing the Filesystem test's ID, so the two
runs report as distinct results.

## 2. Summary

A worker node running SBR in Block volume mode on Ceph RBD is crashed with a
kernel panic. Its peers detect the stalled heartbeat and set
`SBRStorageUnhealthy=True`, NHC creates a `StorageBasedRemediation` CR, a peer
agent fences the node and proves death from storage, and the node reboots and is
restored — the taint removed and the node uncordoned — once NHC deletes the CR.

## 3. Scope

- **In scope**: the full NHC-driven remediation path in Block mode on Ceph RBD —
  storage-based detection (`SBRStorageUnhealthy`), NHC creating the CR, peer
  fencing, `FencingSucceeded`/`Succeeded`, the `out-of-service` taint, reboot
  recovery, and teardown (CR deletion, taint removal, uncordon).
- **Out of scope**:
  - The same flow on RWX **Filesystem** storage (`node_hang.go`, OCP-88738).
  - The watchdog self-fencing path when a node loses storage entirely
    (`storage_loss_watchdog.go`, OCP-88880) and the write-only variant
    (`storage_loss_write_only.go`, OCP-89200).
  - Recovery from a *transient* Ceph RBD partition without fencing
    (`block_storage_transient_partition.go`, RHWA-1924).
  - Block device on-disk layout correctness (`block_storage_inspection.go`,
    RHWA-1926) and concurrent-writer behaviour (`block_storage_rbd.go`, RHWA-1915).
  - Split-brain peer-fencing (`split_brain.go`, OCP-88877).

- `SBR_RBD_STORAGE_CLASS` — the Ceph RBD StorageClass. When unset, a StorageClass
  whose provisioner contains `rbd.csi.ceph.com` is auto-discovered; the test
  **skips** when none exists.
- `SBR_INJECTOR_IMAGE` — image for the privileged injector pod; must ship
  `nsenter`. Defaults to `registry.access.redhat.com/ubi9/ubi:latest`; must be
  mirrored and set in disconnected clusters.

## 5. Preconditions

1. The `NodeHealthCheck` CRD is installed (otherwise the test skips).
2. No pre-existing `NodeHealthCheck` from a prior run of this test
   (`nhc-sbr-block-node-hang`) — it is deleted and waited out in `BeforeAll`.
3. No other `NodeHealthCheck` remediates through the SBR template
   (`requireNoSBRNodeHealthCheck`), which would fence the victim independently.
4. Self Node Remediation is not running (SNR and SBR cannot share the watchdog).
5. A Ceph RBD `volumeMode: Block` StorageClass exists.
6. The Block device-init Job for the test SBRC completes successfully and the
   agent DaemonSet becomes ready.
7. The SBRC reports `status.storageValidation.concurrentWriteable=true`.
8. A schedulable worker node that hosts no SBR controller pod is available to be
   the victim (otherwise the test skips).

## 6. Test steps

| #  | Step (`By` text)                                                                                   | Expected result                                                                 |
| -- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1  | Recording the victim node's boot-id before the kernel panic                                         | Pre-crash boot-id read from the victim                                           |
| 2  | Asserting SBRStorageUnhealthy is not True on the victim node                                        | `SBRStorageUnhealthy` is absent, False or Unknown (not True)                     |
| 3  | Starting a privileged injector pod on node                                                          | Privileged host-PID pod is Running on the victim                                 |
| 4  | Probing that nsenter into PID 1 works and /proc/sysrq-trigger is writable on node                   | Probe succeeds; a failure fails the test (does not skip)                         |
| 5  | Triggering a kernel panic on node via /proc/sysrq-trigger                                           | SysRq crash issued (fire-and-forget; the node panics)                            |
| 6  | Waiting for SBRStorageUnhealthy=True (reason HeartbeatTimeout) on the victim node                   | A peer sets `SBRStorageUnhealthy=True` with reason `HeartbeatTimeout`            |
| 7  | Waiting for NHC to create a StorageBasedRemediation CR for the victim node                          | `StorageBasedRemediation/<victim>` exists                                        |
| 8  | Waiting for FencingSucceeded=True and Succeeded=True on the victim's StorageBasedRemediation CR     | Both conditions reach True (CR re-pulled by name on every poll)                  |
| 9  | Asserting the victim node carries the out-of-service taint                                          | Node has `node.kubernetes.io/out-of-service`                                     |
| 10 | Waiting for the victim node to come back Ready                                                      | Node reports `Ready=True`                                                        |
| 11 | Asserting the victim node's boot-id changed (the node actually rebooted)                            | Post-crash boot-id differs from the pre-crash boot-id                            |
| 12 | Waiting for the victim node's agent pod to be Ready again                                           | This SBRC's agent pod on the victim reaches `PodReady=True`                      |
| 13 | Consistently asserting that the victim is not fenced again (stable boot-id and Ready)               | For 90s the boot-id holds and the node stays `Ready=True`                        |
| 14 | Waiting for NHC to delete the StorageBasedRemediation CR                                            | `StorageBasedRemediation/<victim>` is gone (`IsNotFound`)                        |
| 15 | Asserting the victim node is schedulable again and the out-of-service taint is gone                 | Node is schedulable and carries no `node.kubernetes.io/out-of-service` taint     |

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1931")` runs and passes.
- After the panic, a peer reports `SBRStorageUnhealthy=True` (reason
  `HeartbeatTimeout`) within `StorageInjectionTimeout`.
- NHC creates exactly one `StorageBasedRemediation` named after the victim within
  `NHCSBRCRCreationTimeout`.
- That CR reaches `FencingSucceeded=True` **and** `Succeeded=True` within
  `FencingProvenTimeout`, and the victim carries the
  `node.kubernetes.io/out-of-service` taint.
- The victim returns `Ready` with a changed boot-id, its agent pod reaches
  `PodReady=True`, and for `BlockNoFencingCheckDuration` (90s) it keeps that
  boot-id and stays Ready.
- NHC deletes the CR, and the victim becomes schedulable with the
  `out-of-service` taint removed.
- Cleanup finishes: the NHC, SBRC and injector pod are gone, no
  `StorageBasedRemediation` remains, and the victim is schedulable.

## 8. Failure / known issues

None.

Two design notes, neither a known bug: `FencingInProgress` is deliberately never
asserted, because the 60s fencing window and the 60s heartbeat-staleness threshold
are both hardcoded, so the condition flaps and a `FencingFailed` event is a normal
retry rather than a failure; and the CR is looked up by node name on every poll
because it can be deleted and recreated mid-remediation when `SBRStorageUnhealthy`
cycles to `Unknown`.

## 9. Cleanup

- `AfterAll` removes the `NodeHealthCheck`, force-removes any leftover
  `StorageBasedRemediation` for the victim, uncordons the victim if still
  cordoned, deletes the injector pod, and deletes the SBRC (waiting for it to be
  gone). All tolerate `IsNotFound`.
- Recovery (uncordon) runs even when the spec failed mid-way.
- `BeforeAll` pre-cleans the test's own stale NHC and SBRC from a prior run and
  waits for them to be fully gone before recreating.
