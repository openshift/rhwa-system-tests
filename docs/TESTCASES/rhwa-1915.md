# RHWA-1915 — SBR agents write concurrently to one Ceph RBD block device

## 1. Metadata

| Field                        | Value                                                      |

## 2. Summary

When an SBR config sets `sharedStorageVolumeMode: Block` against a Ceph RBD
StorageClass, the agents on every worker node must attach the same raw device
read-write and write their heartbeats into it at the same time, each reading
back the same heartbeat region.

## 3. Scope

- **In scope**: Block-mode agent rollout on Ceph RBD; concurrent heartbeat
  writes from agents on different nodes into one shared raw device; each agent
  being able to read the whole heartbeat region and parse every written slot.
- **Out of scope**: fencing and remediation in Block mode (RHWA-1916,
  `block_storage_fence_persistence.go`); cross-node read coherence, which is a
  documented non-goal of SBR in both volume modes; filesystem mode, covered by
  the rest of this suite; any backend other than Ceph RBD — the known
  single-writer failure on Portworx is covered upstream, not here.

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator
export ECO_TEST_LABELS='operator:sbr && tier:acceptance'
export SBR_RBD_STORAGE_CLASS=ocs-storagecluster-ceph-rbd
```

`SBR_RBD_STORAGE_CLASS` is optional. When unset, the test discovers a
StorageClass whose provisioner contains `rbd.csi.ceph.com`, and `Skip`s with an
actionable message when the cluster has none. When set to a class that is not
Ceph RBD backed, the test fails rather than silently testing the wrong backend.

## 5. Preconditions

1. SBR operator installed via OLM, controller deployment Ready.
2. Self Node Remediation is not running. SNR and SBR both claim `/dev/watchdog`,
   so the test fails immediately with scale-down instructions rather than
   producing a confusing agent failure later.
3. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one.
4. No `StorageBasedRemediationConfig` named `test-sbrc-block-rbd` left over from
   an earlier run; it is deleted and waited out before a fresh one is created.
5. At least two schedulable worker nodes.

## 6. Test steps

| # | Step (`By` text)                                                            | Expected result                                                                                   |
| - | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1 | Checking if Self Node Remediation (SNR) operator is running                  | No SNR pods Running                                                                                |
| 2 | Discovering Ceph RBD block storage class for Ceph RBD tests                  | A StorageClass with an `rbd.csi.ceph.com` provisioner is resolved                                  |
| 3 | Pre-cleaning stale SBRC "test-sbrc-block-rbd" if present                     | No SBRC of that name remains                                                                       |
| 4 | Creating StorageBasedRemediationConfig "test-sbrc-block-rbd" with Ceph RBD block storage | SBRC admitted with `sharedStorageVolumeMode: Block`                                    |
| 5 | Waiting for SBRC "test-sbrc-block-rbd" agent DaemonSet to be ready           | All scheduled agent pods Ready within `sbrparams.SBRCReadyTimeout`                                 |
| 6 | Verifying all agent pods reach Ready state                                   | Running, Ready agent pods ≥ worker node count within `medik8sparams.DefaultTimeout`                |
| 7 | Validating agent pod count matches worker node count                         | Agent pod count equals worker node count                                                           |
| 8 | Confirming multi-attach capability via Ready pod count                       | At least 2 agents Ready on the same Block device — a single-writer backend could not reach this    |
| 9 | Reading slot data from all agent pods to validate data integrity             | The heartbeat region reads back from every agent pod; each written slot parses with a valid CRC32  |
| 10 | Comparing slot data across all agent pods for consistency                   | The number of written slots seen by each pod agrees within tolerance                               |
| 11 | Validating sequence numbers increment correctly without conflicts           | Heartbeats present from ≥ 2 distinct node IDs, sequences advancing per node                        |

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1915")` runs and passes.
- The agent DaemonSet for the Block-mode SBRC reaches full readiness within
  `sbrparams.SBRCReadyTimeout`, with one Ready pod per worker node.
- Every agent pod can read the heartbeat region off the raw device with
  O_DIRECT, and every slot that carries data has a valid magic, heartbeat
  message type, and CRC32.
- Heartbeats are present from at least two distinct node IDs with advancing
  sequence numbers, so writes from different nodes are both landing on the
  shared device.
- Cleanup finishes: the SBRC is gone, its agent DaemonSet and PVC are garbage
  collected with it, and no node was cordoned, tainted, or rebooted.

## 8. Failure / known issues

None.

## 9. Cleanup

- `DeferCleanup` removes nothing — the `It` creates no cluster resources; it
  only reads the device through existing agent pods.
- `AfterAll` deletes the SBRC created in `BeforeAll` and waits for it to be
  fully gone, tolerating `IsNotFound`. The operator garbage collects the agent
  DaemonSet and the shared PVC with it.
- No recovery steps are needed: the test is non-destructive and never cordons a
  node, injects a fault, or writes to the device.
