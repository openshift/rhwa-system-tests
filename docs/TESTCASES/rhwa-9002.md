## 2. Summary

The WAO manager answers the four FAR admission entries. This test sends FAR requests with server-side dry-run while the FAR operand is `Disabled`, and again while it is `Enabled`, and checks each answer. It also checks the rules that read a Secret and the rules for an update of a stored template.

## 3. Scope

- **In scope**: FAR rules FAR-1 to FAR-10 of `docs/wao-webhooks-test-plan.md`: the action values, the agent inventory that WAO collects from the FAR image, the mandatory parameters, the Secret reads with the WAO ServiceAccount, the template defaulter, and the template update rules. Each create rule is checked in the two operand states.
- **Out of scope**:
  - **The operand controllers.** Remediation, fencing and maintenance belong to the operator
    suites. This spec stores no remediation request and starts no maintenance.
  - **SBR admission.** The SBR operand serves its own webhooks.
  - **CRD schema validation.** A request that the API server rejects before admission does not
    reach a webhook. The operator suites cover those cases.
  - **The agent name pattern `fence_.+`.** The CRD schema rejects it. Specs 71219 and 71220 of
    `tests/far-operator` cover it.
  - **A FenceAgentsRemediation update.** The spec stores no remediation request, so it sends no update of one.

## 5. Preconditions

Asserted in `BeforeAll`:

1. Template `wao-webhook-test-far-template` does not exist. A template from an earlier run is deleted, and
   the spec waits until it is gone.
2. Secret `fence-agents-credentials-shared` does not exist in the namespace. A Secret with the label
   `wao-webhook-test: "true"` is a remainder of this spec and is deleted. A Secret without the label
   belongs to a different owner: the spec fails and does not change it.

The spec accepts each start state of the FAR operand. It records the state and restores it.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("9002")` runs and passes.
- Each request gets the answer in the table, in the `Disabled` state and in the `Enabled` state.
- A denial names the validating entry of the kind.
- The spec stores no `FenceAgentsRemediation`.
- Cleanup finishes: the template and the Secret are gone, and `spec.components.fenceAgentsRemediation.enabled`
  has the value of the start.

## 9. Cleanup

- `DeferCleanup` removes the stored template and the Secret, also after a failure, and tolerates `IsNotFound`.
- `DeferCleanup` sets the FAR operand to the intent of the start. It writes a failure to the log.
- `AfterAll`: none.
- Manual recovery: `oc -n openshift-workload-availability delete fenceagentsremediationtemplate wao-webhook-test-far-template`
  and `oc -n openshift-workload-availability delete secret fence-agents-credentials-shared -l wao-webhook-test=true`.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="component:webhook && operator:wao" \
    --focus="RHWA-9002" ./tests/wao-operator/...
```

The webhook run script selects the spec together with the other webhook specs:

```bash
make run-webhook-tests WEBHOOK_TARGET=far
```

Watch the cluster while it runs:

```bash
watch -n 5 -d tools/watch/webhook-watch.sh   # Linux, or macOS with `brew install watch`
tools/watch/webhook-watch.sh --loop          # anywhere, no `watch` needed
```

What must change: the `fenceAgentsRemediation` row goes `Disabled` → `Available` (and back, when it was
`Disabled` at the start). `ADMIT` stays `true` in each phase. The Secret and the template appear in the
stored objects block for some seconds. What must not change: the webhook entries block, and the
`workload-availability-operator-controller-manager` pods.
