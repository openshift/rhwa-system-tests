## 2. Summary

In `BlockPerNode` mode exactly one process per host may own the watchdog and write the
host journal, and a non-blocking exclusive `flock` on
`/var/lib/medik8s/state/sbr-local-agent.lock` decides which one. This test starts a
second agent process on a node that already runs one and proves all three halves of the
rule: the second process loses the lock, it writes nothing at all — no watchdog, no
journal — and it still reconciles other nodes' remediation requests, because the peer
controller does not depend on the lock. It then replaces the configuration under both
processes and proves the lock file is never unlinked.

## 3. Scope

- **In scope**: the host lock decides the single local-agent owner on a node
  (acceptance criterion 1); the lock file survives configuration replacement without
  being unlinked or changing identity (acceptance criterion 3); a losing agent that also
  cannot write its state still fails safe rather than looking like a success or taking
  the host down.
- **Out of scope**:
  - Acceptance criterion 2, "the lock is acquired before the first watchdog open and
    before the first mutable journal load". The ordering inside the process cannot be
    observed from outside it. The test checks the consequence instead — the loser never
    appears among the lock or watchdog holders and never removes the journal — and the
    ordering itself belongs in an upstream unit test.
  - Acceptance criterion 4, "an unsupported-locking filesystem produces
    `LocalAgentConflict`". Every filesystem under `/var/lib` on this cluster supports
    `flock`, and a read-only mount does not make `flock` fail: it works on a read-only
    file descriptor and on a read-only filesystem. The read-only repeat in this spec
    exercises the *same* branch as the writable one — the real agent holds the lock —
    and adds only that a loser which cannot write its state still fails safe. Both "the
    filesystem does not support locking" and "`flock` fails with no other holder" need
    unit tests with a faked `flock` error.
  - Everything the request on the out-of-selector node would exercise past `Offered`:
    acceptance, boot evidence, `BootEnded`, the out-of-service taint and cleanup. That
    node runs no local agent on purpose, so nothing can accept the offer and nothing
    reboots. The BlockPerNode lifecycle cases in
    [`rhwa-1839`](rhwa-1839.md) cover the rest.
  - Shared `Block` and `Filesystem` modes, which have no host journal and no host lock.

## 5. Preconditions

1. No `NodeHealthCheck` remediates through the SBR template — `requireNoSBRNodeHealthCheck()`
   skips. Such an NHC would create its own `StorageBasedRemediation` CRs for the nodes
   this spec watches.
2. The installed SBR operator accepts `sharedStorageVolumeMode: BlockPerNode` —
   `requireSBRCBlockPerNodeSupport()` skips on an operator that rejects the value in a
   server-side dry-run create, and fails on any other error. **On every build available
   today the spec stops here.**
3. Self Node Remediation is not running — `failIfSNRRunning()` fails. SNR and SBR cannot
   both own the watchdog.
4. Residual Ceph OSD blocklist entries from earlier destructive specs are cleared, before
   the SBRC is created — `clearCephOSDBlocklist()`, best effort.
5. The cluster has a Ceph RBD StorageClass — `discoverCephRBDStorageClass()` skips.
6. At least three schedulable workers exist: two inside the SBRC's selector, so the
   conflicted process is not the only peer, and one outside it as the request target.
7. The conflict node hosts no SBR controller pod — `pickTargetWorkerNode()`.
8. No SBRC named `test-sbrc-bpn-host-lock` and no shadow agent pod is left from an earlier
   run — `deleteSBRCAndWait()` and `deleteHostCommandPod()` remove them and wait.
9. The SBRC's agent DaemonSet is scheduled and Ready on exactly the two labelled nodes,
   and the out-of-selector node runs no agent.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("2065")` runs and passes.
- The second agent process on the conflict node reports
  `sbrparams.LocalAgentConflictReason` within `sbrparams.BlockPerNodeConflictTimeout`,
  in both the writable and the read-only state-mount variant.
- Across the conflict, the host state snapshot on the conflict node keeps the same
  `lock_inode`, the same `lock_holders` PID set and the same `watchdog_holders` PID set:
  the loser owns neither the lock nor the watchdog.
- The losing process keeps running — restart count 0 — and its peer controller processes
  the request created for the out-of-selector node, which reaches
  `sbr.medik8s.io/remediation-owner` phase `Offered` within
  `sbrparams.StorageInjectionTimeout` and is never accepted.
- For `sbrparams.BlockPerNodeQuietCheckDuration` the conflict node keeps its boot-id,
  stays `Ready`, is never `SBRStorageUnhealthy=True` (asserted both live and from the
  recorder, which also catches a value that came and went between polls), never gets an
  execution record, and its real agent neither restarts nor increments
  `sbr_self_fenced_total`.
- Patching `spec.ioTimeout` advances the agent DaemonSet's generation and replaces both agent
  pods. Through that rollout the lock watcher reports
  `SBR_LOCK_STABLE` and never `SBR_LOCK_GONE` or `SBR_LOCK_INODE_CHANGED`, and exactly one
  process holds the lock afterwards.
- Cleanup finishes: both shadow pods, the lock watcher pod and every host-state inspection
  pod are gone; the request is deleted and the out-of-selector node is uncordoned with no
  out-of-service taint; the SBRC and its operands are gone; the test label is off both
  nodes. No node rebooted.

## 8. Failure / known issues

| Issue | Effect | Gate |
| ----- | ------ | ---- |
| `BlockPerNode` is not implemented ([PR #156](https://github.com/medik8s/storage-based-remediation/pull/156) is a proposal under review; RHWA-1839, RHWA-1837) — there is no enum value, no private probe, no host journal, no host lock and no `LocalAgentConflict` reason | The whole spec cannot pass on any current build | `requireSBRCBlockPerNodeSupport()` skips the spec at precondition 2. No env var: the gate is the installed API itself, so the spec starts running by itself once the operator ships the mode |

Three things in the spec come from the design rather than from a build, and must be
re-checked against the merged code before the first real run:

- **The names.** RHWA-2065 says the lock file is
  `/var/lib/medik8s/state/sbr-local-agent.lock` and the reason is `LocalAgentConflict`;
  the design document in PR #156 says `sbr-executor.lock` and `ExecutorConflict`. The
  ticket is newer, so the spec uses its names. If the merged code uses the other pair,
  change `sbrparams.BlockPerNodeLockFileName` and `sbrparams.LocalAgentConflictReason` and
  nothing else.
- **The reporting surface.** The ticket says the second process "reports
  `LocalAgentConflict`" without saying where. Steps 16 and 32 read the pod log, which is
  the only surface certain to exist; step 18 and step 34 read it for the peer manager too.
  The design lists bounded reasons and a writer-conflicts metric, so the merged code will
  probably expose a metric and possibly an event on the config. Prefer the strongest
  surface the code has — `readAgentCounter` or `helpers.WaitForEvents` — and keep the log
  check only as a backup. A log-only assertion is weak and is the reason this test
  departs from the repository's "no log assertions" rule; no other surface is defined yet.
- **Step 20's target.** The design says a peer is eligible when it "uses the config UID
  recorded for the target". If peers only record `Offered` for nodes their own config
  selects, a target outside every selector gets no offer at all and step 20 times out on
  correct code. Confirm how the merged reconciler resolves a target's config. If it
  requires the target to be covered, this half needs a different target that still cannot
  be rebooted — it must not be dropped, it is acceptance criterion 1.

Step 17's journal comparison is the weakest assertion in the spec, because the lock holder
rewrites the journal legitimately on its own schedule: a changed inode between two
snapshots is normal, so only a journal that disappeared is asserted and the rest is
recorded in the report. The lock-holder and watchdog-holder PID sets are the strong
signals — they say which process owns what, which is exactly what the lock decides. Do not
tighten the journal check into an exact inode match without first measuring how often a
healthy agent rewrites it.

## 9. Cleanup

- `DeferCleanup` removes what the `It` created: both shadow agent pods, the lock watcher
  pod, and the remediation request for the out-of-selector node (deleted in the body on a
  passing run; the registered delete is the fallback for a run that failed earlier).
- `DeferCleanup` registered in `BeforeAll` removes the test-only
  `test.medik8s.io/bpn-host-lock` label from both selected nodes, tolerating a missing
  node.
- `AfterAll` force-removes any `StorageBasedRemediation` CR left for the out-of-selector
  node (`cleanupSBRCR`), uncordons that node if recording the offer left it cordoned
  (`uncordonNodeIfNeeded`), deletes the SBRC and waits for its operands
  (`deleteSBRCAndWait`), and clears Ceph OSD blocklist entries (`clearCephOSDBlocklist`).
- Every host-command pod is removed by `runHostCommandPod`'s own `defer`, and
  `createHostCommandPod` removes a same-named leftover before it creates one, so a run
  that died mid-way cannot block the next.
- Recovery runs even when the spec failed mid-way: the uncordon, the CR force-removal and
  the blocklist clear are all `IsNotFound`-tolerant and log warnings with
  `GinkgoWriter.Printf` rather than failing the suite.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="operator:sbr && component:daemonset" \
    --focus="a second agent process on one host loses the lock" ./tests/sbr-operator/...
```

Follow the run with the existing SBR snapshot script — no new watch script is needed, it
already prints every value this spec asserts on:

```bash
watch -n 5 -d tools/watch/sbr-watch.sh   # Linux, or macOS with `brew install watch`
tools/watch/sbr-watch.sh --loop          # anywhere, no `watch` needed
```

| Block | What to look for |
| ----- | ---------------- |
| `=== Nodes ===` — `NAME \| UID \| READY \| CORDON \| FULL BOOT ID \| STORAGE UNHEALTHY \| TAINTS` | The conflict node's `FULL BOOT ID` **must not change** and it must stay `READY=True`, `CORDON=<unset>` and `STORAGE UNHEALTHY=<unset>`. The out-of-selector node **is** expected to show `CORDON=true` from step 20 until step 26, and `TAINTS` must never contain `node.kubernetes.io/out-of-service` on any node. |
| `=== SBR requests ===` — `NAME \| UID \| TARGET \| CONDITIONS \| CLEANUP \| START \| DEADLINE` | One request named after the out-of-selector node, appearing at step 19 and gone after step 26. Its `UID` is the one that must show up in the target Node's `sbr.medik8s.io/remediation-owner` annotation. |
| `=== Agent and reporter Pods ===` — `NAME \| UID \| NODE \| PHASE \| CONTAINER READINESS` | `sbr-shadow-agent-<node>` is `Running` with `sbr-agent=false` and `restarts:0` — that is the pass case, not a problem. Both `sbr-agent-test-sbrc-bpn-host-lock-*` pods change `UID` exactly once, at step 28, and the real agent on the conflict node must keep `restarts:0` throughout. |

The `UID` columns are what make this test followable: the whole spec turns on pod and request
identity, and a name alone cannot tell a replaced agent from a surviving one.

Record the conflict node's boot ID **before** starting the run: that is what step 22
compares against, and a changed boot ID is the loudest possible failure of this test — it
means the losing process opened the watchdog.
