# RHWA-2039 — Fencing is withheld while the storage write check has not passed on Ceph RBD block storage

## 1. Metadata

| Field                        | Value                                                                  |
| ---------------------------- | ---------------------------------------------------------------------- |
| Jira                         | [RHWA-2039](https://issues.redhat.com/browse/RHWA-2039)                |
| `reportxml.ID`               | `2039`                                                                 |
| Polarion (legacy) — OPTIONAL | None                                                                   |
| Operators                    | SBR v5.8.0 (no NHC — the spec creates the remediation CR itself)       |
| Suite                        | `tests/sbr-operator`                                                   |
| Spec file                    | `tests/sbr-operator/tests/block_storage_write_gate.go`                 |
| Author                       | rwurmbra                                                               |
| Status                       | draft                                                                  |

Before a peer agent cordons or fences anything, the remediation reconciler reads
`status.storageValidation.concurrentWriteable` on its SBRC. The operator sets it
once at least `min(2, desired)` agents are Ready, which is the cluster's
evidence that the shared device takes concurrent writes. While it is unset the
reconciler emits a `FencingWithheld` Warning event on the CR, changes nothing,
and requeues after 10s. Every other Block-mode spec only runs with that gate
open. This one keeps it closed and checks that a remediation CR is withheld.

## 2. Summary

Every agent but one is kept from becoming Ready, so the SBRC never confirms
concurrent writeability. A `StorageBasedRemediation` CR is then created for a
blocked worker. The reconciler must emit `FencingWithheld` on the CR and must
not cordon, fence, or taint the node.

## 3. Scope

- **In scope**: The storage write gate in the remediation reconciler, in Block
  mode on Ceph RBD. While `concurrentWriteable` is not true, a
  `StorageBasedRemediation` CR gets a `FencingWithheld` Warning event naming the
  victim. For `BlockNoFencingCheckDuration` the victim stays schedulable with no
  `out-of-service` taint, the CR never reports `FencingInProgress=True` or
  `FencingSucceeded=True`, and no fence message appears anywhere in the fence
  region.
- **Out of scope**:
  - The gate open and fencing running for real — fence slot geometry
    (`block_storage_fence_geometry.go`, RHWA-2031) and real faults
    (`block_storage_split_brain.go`, RHWA-1934; `block_storage_node_hang.go`,
    RHWA-1931).
  - The gate never opening because shared storage really rejects concurrent
    writes (Portworx shared block). That is covered upstream by the e2e test
    `testStorageWriteCheckWithheldBlockModePortworx`. This spec closes the gate
    by blocking agents with a held watchdog, not with a broken backend.
  - The gate on RWX **Filesystem** storage. The reconciler check is the same
    code in both volume modes; this spec only runs it in Block mode.
  - The gate clearing again when the DaemonSet grows past `probedNodeCount`, and
    staying set through readiness dips once it is true.
  - Detect-only mode withholding the remediation before it reaches the gate
    (`detect_only.go`, OCP-88876). Detect-only must stay disabled here, see
    section 8.
  - NHC creating the CR. No `NodeHealthCheck` is involved.

## 5. Preconditions

1. No `NodeHealthCheck` remediates through the SBR template
   (`requireNoSBRNodeHealthCheck`). Otherwise the spec skips.
2. The installed SBR CRD has `sharedStorageVolumeMode`
   (`requireSBRCBlockVolumeModeSupport`). Otherwise the spec skips.
3. Self Node Remediation is not running (SNR and SBR cannot share the watchdog).
   Otherwise the spec fails with instructions to scale SNR down.
4. Residual Ceph OSD blocklist entries from earlier specs are cleared before the
   SBRC exists. This is best-effort and never fails the spec.
5. A Ceph RBD `volumeMode: Block` StorageClass exists. Otherwise the spec skips.
6. At least 2 schedulable workers exist. Otherwise the spec skips.
7. A schedulable worker hosts no SBR controller pod, to be the victim.
   Otherwise the spec skips.
8. Any SBRC named `test-sbrc-block-write-gate` and any watchdog-keepalive pods
   left by a previous run are deleted and waited out before anything is
   recreated.
9. Before the SBRC exists, a keepalive pod holds `/dev/watchdog` open on every
   Ready worker except the unblocked one, and has confirmed it holds it. This
   includes cordoned workers, because the agent DaemonSet tolerates cordons
   and would otherwise run a Ready agent there.
10. The Block device-init Job for the SBRC succeeds.
11. The agent on the unblocked worker becomes Ready.
12. The agent DaemonSet desires at least 2 pods and has exactly 1 Ready.
13. `status.storageValidation.concurrentWriteable` on the SBRC is not true.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("2039")` runs and passes.
- Before the CR exists, the agent DaemonSet has at least 2 desired pods and
  exactly 1 Ready, and the SBRC does not report `concurrentWriteable=true`.
- Within `StorageInjectionTimeout` (3m) of the CR being created, a Warning
  `FencingWithheld` event involving that CR's UID has a message containing
  `Withholding fencing for node '<victim>'`.
- For `BlockNoFencingCheckDuration` (90s), checked every
  `BlockNoFencingCheckInterval` (10s): `concurrentWriteable` stays not true, the
  victim stays schedulable with no `node.kubernetes.io/out-of-service` taint, the
  CR never reports `FencingInProgress=True` or `FencingSucceeded=True`, and every
  slot in the fence region read through the observer agent parses and carries
  `FENCE_REASON_NONE`.
- Cleanup finishes: no `StorageBasedRemediation` remains for the victim, the
  victim is uncordoned, no keepalive pod remains, and the SBRC is gone.

## 8. Failure / known issues

None.

Design notes, none of them a known bug:

- Detect-only must stay disabled. Detect-only agents skip the watchdog check,
  so the keepalives would not block them, and the reconciler would withhold the
  remediation for detect-only before ever reaching the gate.
- The keepalives must hold the watchdog before the SBRC is created. Once
  `concurrentWriteable` is true, the operator keeps it true through readiness
  dips, so blocking agents afterwards would not close the gate.
- Blocking relies on agent preflight failing when the watchdog check fails.
  A held watchdog makes the open fail, and because the device exists, no
  softdog fallback is tried. The agent exits and never writes its readiness
  sentinel.
- The observer is picked by node, not as "any agent off the victim". A blocked
  agent's pod is briefly Running each time it restarts, so a lookup that way
  could pick one that is about to exit.
- The schedulable check is the main signal, because cordoning is the first thing
  the reconciler does after the gate. The fence region check backs it up but is
  weak on its own here: the victim's agent never registered in the node map, so
  even a reconciler that skipped the gate would fail to resolve the victim's
  node ID and write nothing.
- The CR does get the SBR finalizer, since the reconciler adds it before the
  gate. The agent on the unblocked node removes it on delete, so a plain delete
  works.

## 9. Cleanup

- There is no `DeferCleanup`. Everything the spec creates, including the CR from
  the `It`, is removed in `AfterAll`, in this order:
  1. Delete the `StorageBasedRemediation` CR and poll until it is gone, for up
     to `SBRCRCleanupTimeout`. If it is still there, force-remove it
     (`cleanupSBRCR`).
  2. Uncordon the victim if it is still cordoned.
  3. Delete the keepalive pods.
  4. Delete the SBRC and wait for it to be gone.
  5. Clear Ceph OSD blocklist entries (best-effort).
- The order matters. The CR is deleted before the keepalive pods: once they are
  gone, the blocked agents start, the gate opens, and a CR that still existed
  would be fenced for real against a victim that is now registered.
- All steps tolerate `IsNotFound` and log rather than fail. The CR wait is
  polled rather than asserted, so a timeout there does not abort the rest of
  `AfterAll` and leak keepalive pods or the SBRC.
- Recovery runs even when the spec failed mid-way.
- `BeforeAll` pre-cleans this spec's own stale SBRC and keepalive pods from a
  previous run and waits for them to be fully gone before recreating them.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="operator:sbr && component:remediation" \
    --focus="storage write check has not passed in Block mode" ./tests/sbr-operator/...
```

There is no `tools/watch` script for SBR yet. To follow the run live, watch the
agent DaemonSet, the SBRC gate, the victim node and the CR:

```bash
watch -n 5 -d '
oc -n openshift-workload-availability get ds sbr-agent-test-sbrc-block-write-gate \
    -o custom-columns=DESIRED:.status.desiredNumberScheduled,READY:.status.numberReady
oc -n openshift-workload-availability get storagebasedremediationconfig test-sbrc-block-write-gate \
    -o custom-columns=WRITEABLE:.status.storageValidation.concurrentWriteable
oc get nodes -l node-role.kubernetes.io/worker \
    -o custom-columns=NAME:.metadata.name,UNSCHED:.spec.unschedulable,TAINTS:.spec.taints[*].key
oc -n openshift-workload-availability get events \
    --field-selector reason=FencingWithheld --sort-by=.lastTimestamp | tail -3
'
```

What must not change: `READY` stays `1` and `WRITEABLE` stays empty for the
whole run. No worker shows `UNSCHED=true` or an `out-of-service` taint. What
must change: once the CR exists, a `FencingWithheld` event appears and repeats
about every 10s. Blocked agent pods restarting in a loop is expected until the
keepalive pods are deleted in `AfterAll`.
