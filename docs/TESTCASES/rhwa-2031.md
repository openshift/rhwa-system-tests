# RHWA-2031 — Fence slot geometry on Ceph RBD block storage

## 1. Metadata

| Field                        | Value                                                                  |
| ---------------------------- | ---------------------------------------------------------------------- |

| Author                       | rwurmbra                                                               |

This is a regression test for the reconciler/agent slot offset mismatch fixed
upstream in `4131c812`. In Block mode the agent reads its own fence slot at
`(nodeID - 1) * 4096`, while the controller wrote at `nodeID * slotSize`: the
fence landed one slot past the victim, so the victim never saw it, and the
completion check read the neighbour's heartbeat slot — which, being zero-filled,
fails to unmarshal and counts as "stopped". Fencing was therefore reported as
succeeded while the victim was still alive. The unit tests
(`TestSlotOffsetAgreesWithReconciler`, `storagebasedremediation_fencewrite_test.go`)
guard the arithmetic; this spec guards the behaviour end to end on real Ceph RBD.

## 2. Summary

A `StorageBasedRemediation` CR is created for one worker node running SBR in
Block volume mode on Ceph RBD, and the fencing is allowed to run for real. The
fence message must land in the slot the victim's own agent reads, the victim
must act on it and reboot, and the controller must only report fencing as
succeeded after the victim's heartbeat has actually stopped.

## 3. Scope

- **In scope**: Block-mode fence slot geometry on Ceph RBD — the fence message
  appears in fence slot index `nodeID-1` and targets the victim's node ID, the
  slot after it stays untouched, the victim acts on the fence and reboots, and
  `FencingSucceeded`/`Succeeded` are only reported after the victim's heartbeat
  slot has fallen behind the rest of the device. Also the recovery path: the
  out-of-service taint, deleting the CR, and the agent coming back.
- **Out of scope**:
  - Fencing driven by a real fault and by NHC — storage isolation
    (`block_storage_split_brain.go`, RHWA-1934) and a kernel panic
    (`block_storage_node_hang.go`, RHWA-1931). This spec injects no fault at
    all: it creates the CR directly, so only the geometry is under test.
  - The same geometry on RWX **Filesystem** storage, where slots are
    `nodeID * 512` and slot 0 is unused (`split_brain.go`, OCP-88877).
  - The watchdog self-fencing path when a node loses storage entirely
    (`storage_loss_watchdog.go`, OCP-88880).
  - Static on-disk layout correctness — superblock, node map, slot-to-node-ID
    agreement on an idle cluster (`block_storage_inspection.go`, RHWA-1926).
  - Detect-only mode. Since `6c98b1cd` (2026-11-01) the controller withholds
    cordon, fence and taint when `detectOnlyMode` is Enabled, so that mode
    cannot be used to keep the victim alive while a fence is written
    (`detect_only.go`, OCP-88876, covers the suppression itself).

## 5. Preconditions

1. No `NodeHealthCheck` remediates through the SBR template
   (`requireNoSBRNodeHealthCheck`) — one would create and delete its own CRs for
   the node this spec fences by hand. Otherwise the spec skips.
2. Self Node Remediation is not running (SNR and SBR cannot share the watchdog).
   Otherwise the spec fails with instructions to scale SNR down.
3. A Ceph RBD `volumeMode: Block` StorageClass exists; otherwise the spec skips.
4. Any SBRC named `test-sbrc-block-fence-geometry` from a previous run is
   deleted and waited out before the spec recreates it.
5. The Block device-init Job for that SBRC completes successfully.
6. The agent DaemonSet becomes ready.
7. The SBRC reports `status.storageValidation.concurrentWriteable=true` — until
   it does, the controller withholds fencing and no fence is ever written.
8. The SBRC has agent pods on at least 2 nodes; otherwise the spec skips.
9. An agent node without an SBR controller has an unassigned following node ID,
   or owns the last slot in the region. The highest eligible ID is preferred;
   a lower ID with a gap preserves the same empty-neighbour check. The spec
   skips only when no eligible victim exists. Before fencing, the actual fence
   and heartbeat slots after the victim must still be verified zero-filled.
10. An observer agent pod on a node other than the victim is available to read
    the shared device.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("2031")` runs and passes.
- Before the remediation exists, the victim's fence slot (index `nodeID-1`) asks
  for nothing, and the fence and heartbeat slots at index `nodeID` are
  zero-filled.
- Within `BlockFenceWriteTimeout` (3m) a valid SBD fence message appears in fence
  slot index `nodeID-1` with `TargetNodeID` equal to the victim's node ID, and the
  slot at index `nodeID` is still zero-filled in the same read.
- Within `BlockVictimHeartbeatStallTimeout` (5m) the victim's heartbeat slot falls
  more than `BlockHeartbeatStallQuietPeriod` (45s, three write cycles) behind the
  newest heartbeat on the device, and no `FencingSucceeded=True` is observed while
  that slot is less than `BlockHeartbeatSlotMaxAge` (30s, two write cycles) behind.
- Within `FencingProvenTimeout` (10m) the CR reports `FencingSucceeded=True` and
  `Succeeded=True`, the `FencingSucceeded` transition is later than the last
  heartbeat the victim wrote, and the victim carries the
  `node.kubernetes.io/out-of-service` taint.
- Within `NodeRebootTimeout` (20m) the victim's boot-id changes and it returns
  `Ready=True`; after the CR is deleted it becomes schedulable with the taint
  removed, and within `BlockAgentReadyAfterRebootTimeout` (10m) its agent pod
  reaches `PodReady=True`.
- Cleanup finishes: no `StorageBasedRemediation` remains for the victim, the
  victim is uncordoned, and the SBRC is gone.

Both staleness figures are measured between timestamps written on the device by
the nodes themselves — the victim's slot against the newest slot on the device —
never against the test runner's clock or against when a read returned. An exec
into the observer pod has been seen to stall for tens of seconds, and a measure
anchored to read time turns that stall into a false "the victim stopped".

## 8. Failure / known issues

None.

The highest node ID is not required: a non-controller agent node whose following
ID is unassigned exercises the same offset error. Assigned following IDs are
excluded so the test cannot mistake another agent's valid data for an off-by-one
write. On-device checks still require the neighbouring slots to be empty.

Two design notes, neither a known bug. `FencingInProgress` is deliberately never
asserted: the fencing monitor window and the heartbeat staleness threshold are
both hardcoded at 60s, so the condition flaps and a `FencingFailed` event is a
normal retry. And the spec deletes the remediation CR itself once the victim is
Ready, before waiting for the agent pod: the `out-of-service` taint evicts the
Ceph RBD CSI node plugin, so until the CR is deleted the agent cannot attach the
shared device and stays in `ContainerCreating` — waiting for it first deadlocks.

## 9. Cleanup

- `DeferCleanup` deletes the victim's `StorageBasedRemediation` CR and waits for
  the node to be schedulable with no `out-of-service` taint. On a run that got as
  far as step 23 this is a no-op; on one that failed earlier it is what restores
  the node. The delete is a plain one, not a force-removal, because the
  reconciler's finalizer is what uncordons and untaints.
- `AfterAll` force-removes any `StorageBasedRemediation` left for the victim
  (`cleanupSBRCR`, which strips finalizers and then restores the node),
  uncordons the victim if it is still cordoned, and deletes the SBRC, waiting
  for it to be gone. All tolerate `IsNotFound` and log rather than fail.
- Recovery runs even when the spec failed mid-way: a failure between the CR
  creation and the reboot leaves a cordoned, tainted node, and both cleanup
  paths above undo exactly that.
- `BeforeAll` pre-cleans this spec's own stale SBRC from a previous run and
  waits for it to be fully gone before recreating it.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="operator:sbr && component:remediation" \
    --focus="the fence reaches the slot the victim reads" ./tests/sbr-operator/...
```

Record the victim's boot ID before starting — that is what step 21 compares
against. What must change, in this order: the victim is cordoned, its CR shows
`FencingInProgress=True`, `Ready` goes `Unknown`, the `out-of-service` taint
appears with `FencingSucceeded=True` and `Succeeded=True`, and the boot ID
changes last. What must not: no other node is cordoned, tainted or reboots, and
`status.storageValidation.concurrentWriteable` on the SBRC must read `true` from
before the CR is created — while it does not, fencing is withheld and nothing is
written to the device.

Follow the run with the read-only snapshot:

```bash
tools/watch/sbr-watch.sh --loop -n 5
```

Compare boot IDs with the baseline: only the selected victim may reboot.

The victim's agent pod sitting in `ContainerCreating` after the reboot is
expected until the CR is deleted and the taint goes.
