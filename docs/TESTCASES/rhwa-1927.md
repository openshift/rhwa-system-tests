Covers the product bug [RHWA-1384](https://redhat.atlassian.net/browse/RHWA-1384), fixed by
[self-node-remediation#339](https://github.com/medik8s/self-node-remediation/pull/339).

## 2. Summary

A control plane node whose local kube-apiserver still answers `/readyz?exclude=shutdown`
with 200, but whose SNR agent cannot reach any peer agent, must detect its own isolation and
reboot itself. Before the fix the passing `/readyz` reset the agent's error count on every
tick, so an isolated control plane node fed its watchdog forever and was never remediated.

### Cross-check against the expected behaviour on RHWA-1384

The customer stated the expected behaviour as five steps. Each maps to an assertion:

| # | Customer's expected behaviour | Where it is asserted | Observable |
| - | ----------------------------- | -------------------- | ---------- |
| 1 | The agent's independent API connectivity check should detect that the node is isolated. | Step 6 | `CP node: readyz passed but no CP peers reachable` in the victim agent's log. |
| 2 | After `maxApiErrorThreshold` (3) consecutive failures, the agent should consult peers. | Step 5 | `Error count exceeds threshold, trying to ask other nodes if I'm healthy`. |
| 3 | Peers should confirm the node is unhealthy, **or be unreachable, triggering the `MaxTimeForNoPeersResponse` fallback**. | The injection itself | This test drives the second half of that "or": every peer is unreachable, so `getWorkerPeersResponse` falls through to the `maxTimeForNoPeersResponse` check and returns `UnHealthyBecauseNodeIsIsolated`. The first half (peers confirm unhealthy) is the `cpUnhealthy` branch and is out of scope. |
| 4 | The agent should stop feeding the watchdog. | Step 7 | `CP isolation detected despite passing readyz, triggering reboot`, logged at the point the agent calls `Rebooter.Reboot()`. |
| 5 | The hardware watchdog should fire and reboot the node, **within ~2 minutes**. | Steps 8 and 9 | `status.nodeInfo.bootID` changes, and the measured elapsed time is asserted against `snrparams.CPIsolationRebootSLA`. |

Two points where this test is deliberately stricter or looser than the ticket text:

- **Step 4 needs its own assertion.** `CP node: readyz passed but no CP peers
  reachable` is logged on *every* tick once peers are unreachable, including ticks
  where the agent then logs `not all peers confirmed isolation, waiting for
  threshold` and does nothing. Asserting only that message would pass on a build
  that detects isolation but never reboots — which is most of the bug. The
  reboot-trigger message is what proves the watchdog stopped being fed.
- **The ~2 minute figure is asserted with headroom, not literally.**
  `CPIsolationRebootSLA` is 4 minutes. The defaults support ~2 minutes (see the
  timing note in section 12), and the measured value is recorded with
  `AddReportEntry` on every run so latency regressions stay visible, but asserting
  120s exactly would flake on a loaded cluster for no diagnostic gain. A run that
  takes 4 minutes indicates a real regression; one that takes 150s does not.

## 3. Scope

- **In scope**: the agent-side isolation gate added in `internal/apicheck/check.go`. With
  `/readyz` returning 200 on a control plane node, no reachable peer agent, and a non-empty
  cached control plane peer list, the agent must stop feeding the watchdog and the node must
  reboot on its own.
- **Out of scope**:
  - Any path where `/readyz` fails. That is the pre-existing branch at `check.go:99`,
    exercised by OCP-55059 (`master_remediation.go`).
  - The NHC → `SelfNodeRemediation` → reboot path for a control plane node. This test runs
    with no NHC selecting control plane nodes and skips when one exists; otherwise NHC could
    legitimately remediate the node and the test would pass without the code under test ever
    running.
  - Worker node behaviour, which PR #339 leaves unchanged and which OCP-52416 covers.
  - The `cpUnhealthy` branch (`check.go:123`), where a peer control plane node already holds
    an SNR CR for this node. OCP-55059 reaches that branch incidentally; it is not asserted
    there and this test does not assert it either.
  - The false positive the fix knowingly accepts: on a 3-master cluster where two masters are
    genuinely down rather than isolated, the survivor self-reboots. See section 8.

### Why the fault is injected inside the agent pod's network namespace

The SNR agent DaemonSet (`install/self-node-remediation-deamonset.yaml`) sets `hostPID: true`
but **not** `hostNetwork`, and `HostPort` (default 30001) is only a `containerPort`. Peer
addresses are therefore agent **pod** IPs on the cluster SDN, and on OVN-Kubernetes that
traffic leaves the node Geneve-encapsulated. Host-namespace iptables rules matching
`--dport 30001` would never see it, so the usual pattern from the SBR suite — rules injected
with `nsenter --target 1 --net` — does not work here.

Instead the test locates the agent process on the victim node (`pgrep -f` for
`/manager --is-manager=false`, visible because the agent shares the host PID namespace) and
runs `nsenter -t <pid> -n -- iptables` to add a REJECT rule for TCP 30001 inside the agent's
own network namespace. Consequences worth stating:

- It is the minimal fault that reproduces the reported condition. The kube-apiserver
  connection lives in the same namespace on a different port and is untouched, so `/readyz`
  provably keeps returning 200 — which is the precondition the whole fix is about.
- Kubelet, etcd and every other workload on the node are unaffected, so the node stays
  `Ready` and nothing outside SNR has a reason to remediate it. That is what makes the
  reboot attributable to the code under test.
- Peer agents keep running and keep appearing in the victim's cached peer list, so the
  `peersExist` guard at `check.go:133` holds for the whole run. Approaches that remove the
  peer agents instead (node labels, scaling the DaemonSet) race `peerUpdateInterval`: once
  the list empties the gate stops firing, and the test becomes timing-dependent.
- The rules die with the pod. When the node reboots, the agent comes back with a fresh
  network namespace and no rules; the flush path in section 9 only matters for a run that
  failed before the reboot.

## 5. Preconditions

Asserted in `BeforeAll`:

1. At least `snrparams.MinReadyMasterNodes` (3) Ready control plane nodes, so that rebooting
   one keeps etcd quorum. Fewer, and the spec skips rather than destroying the cluster.
2. No `NodeHealthCheck` selects control plane nodes. One would remediate the victim through
   the ordinary NHC path and the reboot would no longer prove the isolation gate ran, so the
   spec skips rather than reporting a false pass.
3. The default `SelfNodeRemediationConfig` exists and the agent DaemonSet has a Running,
   Ready pod on every control plane node — the victim needs a running agent, and the peers it
   will fail to reach must be real.
4. The peer health port is read from `SelfNodeRemediationConfig.spec.hostPort` rather than
   assumed, so a cluster that moved it off the 30001 default is still blocked correctly.
5. A probe pod proves, on the victim node, that the agent process can be found by `pgrep` and
   that `nsenter -t <pid> -n -- iptables -L OUTPUT -n` succeeds. A node where either fails
   skips instead of failing mid-test.
6. Any injector or flush pod left by an earlier run is deleted and fully gone before a new
   one is created.
7. No `SelfNodeRemediation` CR exists for the victim node.

## 6. Test steps

| #  | Step (`By` text)                                                                                       | Expected result                                                                                 |
| -- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1  | Recording boot ID and creation timestamp for every control plane node                                       | `status.nodeInfo.bootID` and `metadata.creationTimestamp` are read and non-empty for the victim and every peer master |
| 2  | Confirming the victim agent reports no API error before the partition                                       | `failed to check api server` is absent from the victim agent's recent log                            |
| 3  | Blocking the SNR peer health port inside the victim agent's network namespace                               | The injector pod reaches Succeeded; the elapsed-time clock for the RHWA-1384 budget starts here      |
| 4  | Confirming the victim node stays Ready while its agent is isolated                                          | `Ready=True` holds for `snrparams.CPIsolationReadyGraceDuration`, proving `/readyz` still passes      |
| 5  | Waiting for the victim agent to consult its peers after crossing the error threshold                        | `Error count exceeds threshold, trying to ask other nodes if I'm healthy` within `snrparams.CPIsolationDetectTimeout` |
| 6  | Waiting for the victim agent to log that readyz passed but no control plane peers are reachable             | `CP node: readyz passed but no CP peers reachable` within `snrparams.CPIsolationDetectTimeout`        |
| 7  | Waiting for the victim agent to stop feeding the watchdog and trigger a reboot                              | `CP isolation detected despite passing readyz, triggering reboot` within `snrparams.CPIsolationDetectTimeout` |
| 8  | Waiting for the victim node's boot ID to change                                                             | A new `status.nodeInfo.bootID` within `snrparams.CPIsolationRebootTimeout`; the elapsed time is recorded with `AddReportEntry` |
| 9  | Verifying the reboot met the remediation time budget from RHWA-1384                                         | Elapsed time from step 3 is under `snrparams.CPIsolationRebootSLA`                                   |
| 10 | Verifying the victim node was rebooted and not deleted or recreated                                         | `metadata.creationTimestamp` equals the value recorded in step 1                                     |
| 11 | Verifying no SelfNodeRemediation CR was created for the victim node                                         | `SelfNodeRemediation/<victim>` is `IsNotFound`, so the reboot came from the agent's own isolation gate and not from NHC |
| 12 | Waiting for the victim node to become Ready                                                                 | `Ready=True` within `snrparams.NodeReadyTimeout`                                                     |
| 13 | Verifying the surviving control plane nodes never rebooted                                                  | Every other control plane node keeps the boot ID recorded in step 1                                  |
| 14 | Verifying SNR DaemonSet pods are running again                                                              | `verifyDSPodsRunning` succeeds within `snrparams.DSPodRestartTimeout`                                |

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1927")` runs and passes.
- While its agent's peer health port is blocked, the victim keeps `Ready=True` for
  `snrparams.CPIsolationReadyGraceDuration`. This is what makes the test meaningful: it proves
  `/readyz` was still returning 200 at the moment the agent decided to reboot.
- The victim agent logs, in order and each within `snrparams.CPIsolationDetectTimeout`:
  peer consultation after the error threshold, the isolation detection, and the reboot
  trigger. The last of the three is what proves the agent stopped feeding the watchdog
  rather than merely noticing the isolation.
- The boot ID changes within `snrparams.CPIsolationRebootSLA` of the peer port being
  blocked, which is the RHWA-1384 expectation of ~2 minutes carried with headroom. The
  measured value is attached to the report on every run.
- The victim's `status.nodeInfo.bootID` changes within `snrparams.CPIsolationRebootTimeout`
  while `metadata.creationTimestamp` is unchanged, so the node rebooted rather than being
  deleted and recreated.
- No `SelfNodeRemediation` CR exists for the victim at any point, so the reboot is
  attributable to the agent's isolation gate rather than to NHC.
- Every other control plane node keeps its original boot ID, so the remediation did not
  cascade across the control plane.
- The victim returns `Ready=True` within `snrparams.NodeReadyTimeout` and the agent DaemonSet
  is fully Running again within `snrparams.DSPodRestartTimeout`.
- Cleanup finishes: the injector and flush pods are gone and no REJECT rule for the peer
  health port remains in the victim agent's network namespace.

On a build without PR #339 this spec fails at step 5 and then step 6: the passing `/readyz`
resets `errorCount` on every tick and the node never reboots. That is the regression it exists
to catch.

## 8. Failure / known issues

| Issue | Effect | Gate |
| ----- | ------ | ---- |
| The isolation gate cannot distinguish "I am isolated" from "my peers are gone". `check.go:135` documents this: on a 3-master cluster where two masters are genuinely down, the survivor sees no reachable peer and self-reboots. | A rolling control plane reboot — a cluster upgrade, or two concurrent master remediations — could in principle reboot a healthy survivor. | Not gated; this test does not reproduce it. It reboots exactly one master and asserts in step 10 that the others stay up, which is the narrow version of the concern that is safe to assert here. A test for the rolling-reboot case belongs in its own ticket. |
| `getControlPlanePeersStatus()` runs twice per tick on the isolation path — once in `Start` and again inside `isConsideredHealthy`. | Harmless here because the test uses REJECT, so each dial fails immediately. In a real blackhole isolation each round costs `peerDialTimeout` per peer, so detection in the field is slower than this test measures and may exceed the ~2 minutes on the ticket. | Not a gate. The test cannot measure the blackhole case without becoming slow and flaky; worth raising upstream as a separate observation. |

The spec is not gated behind an env var: the behaviour under test is fixed in SNR v5.8.0 and
the spec is expected to pass on any build carrying PR #339.

## 9. Cleanup

- `DeferCleanup` runs a flush pod on the victim that re-enters the agent's network namespace
  and deletes each REJECT rule with `|| true`, then deletes the injector and flush pods. It
  tolerates the agent PID having changed or vanished — after the reboot there is nothing to
  flush, and the helper logs with `GinkgoWriter.Printf` rather than failing.
- `DeferCleanup` then waits for the victim to be `Ready=True` again, so a later spec does not
  start against a cluster with a master still booting.
- `JustAfterEach` is the safety net, following the pattern already used in
  `master_remediation.go`: delete any leftover `SelfNodeRemediation` CR for the victim, wait
  for the node to be Ready, and `Eventually(verifyDSPodsRunning)`. A failure to recover is
  recorded with `AddReportEntry` rather than failing the suite a second time.
- Every host-command pod deletes a same-named leftover before it starts, so a run that was
  killed mid-spec does not block the next one.

New constants in `tests/snr-operator/internal/snrparams/const.go`, and a new
`snrparams.InjectorImage` var mirroring `sbrparams.InjectorImage`:

| Constant                        | Value | Why                                                                                                                 |
| ------------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------- |
| `CPIsolationReadyGraceDuration` | `45s` | Three `apiCheckInterval` ticks — long enough to show the node is still serving, short enough to finish before the reboot. |
| `CPIsolationDetectTimeout`      | `5m`  | See the timing note below.                                                                                           |
| `CPIsolationRebootTimeout`      | `10m` | Detection, then the watchdog fires and the master posts.                                                             |
| `CPIsolationPodTimeout`         | `3m`  | Budget for a one-shot injector/flush/probe pod to pull its image and finish.                                         |
| `CPIsolationLogWindow`          | `10m` | How far back `GetLog` reads when searching the agent log.                                                            |

Recovery reuses `snrparams.NodeReadyTimeout` (15m) and `snrparams.DSPodRestartTimeout` (15m)
rather than adding more.

The detection budget comes from the SNRC defaults in `selfnoderemediationconfig_types.go`:

- `apiCheckInterval` 15s — the poll loop in `check.go:83`.
- `maxApiErrorThreshold` 3 — the new branch calls `isConsideredHealthy()`, which calls
  `getWorkerPeersResponse()`, which increments `errorCount` once per tick and returns
  `HealthyBecauseErrorsThresholdNotReached` until the third. The branch returns before
  `c.errorCount = 0`, so the count accumulates across ticks: roughly 45s.
- `maxTimeForNoPeersResponse` 30s — measured from the last successful peer response, which
  is moments before the block. Only after it elapses with no peer response at all does
  `getWorkerPeersResponse` return `UnHealthyBecauseNodeIsIsolated`, the single reason that
  makes `IsControlPlaneHealthy` return `canOtherControlPlanesBeReached` — false here — and
  so trigger the reboot.
- `peerDialTimeout` 5s and `peerRequestTimeout` 7s — **not** paid by this test. REJECT
  produces an immediate refusal, so dials fail in milliseconds and ticks stay at 15s. This
  is why the ~2 minute figure on RHWA-1384 is reachable here: ~45s to cross the threshold,
  with the 30s no-peers window already satisfied by then, leaves the watchdog timeout as the
  remaining cost. DROP would instead cost `peerDialTimeout` per peer per round, twice per
  tick, and push detection well past two minutes — one more reason the injection uses
  REJECT.
- `peerUpdateInterval` 15m — far longer than the run, so the cached peer list stays populated
  and the `peersExist` guard holds.

One consequence of that chain is worth repeating, because getting it wrong produces a
confusing red test: the block must cut the victim off from **worker peers as well as control
plane peers**. If worker agents stayed reachable they would answer `HealthyBecauseCRNotFound`,
and `IsControlPlaneHealthy` returns `true` for that reason regardless of
`canOtherControlPlanesBeReached`, so the node would never reboot. A single REJECT rule on the
peer health port inside the agent's namespace covers every peer at once, which is why it is
expressed that way rather than per-peer-IP.
