The product bug behind this is [RHWA-1184](https://redhat.atlassian.net/browse/RHWA-1184)
(`ON_QA`), the 5.0 recurrence of the already-`Closed` [RHWA-1068](https://redhat.atlassian.net/browse/RHWA-1068) — same root cause,
same fix: `runPreflightChecks()` in `cmd/sbr-agent/main.go` checked the watchdog device
before checking `detectOnlyMode`, so a busy `/dev/watchdog` (e.g. held by SNR) crashed the
agent even though detect-only mode never arms a real watchdog.

RHWA-1933 replaces [RHWA-1187](https://redhat.atlassian.net/browse/RHWA-1187), which was
opened as this same test-case ticket but as a `Sub-task` — a type `check-testcase-jira`
rejects, and which Jira does not allow converting to a `Task` in place (confirmed: editing
the issue type field returns `InvalidPayloadException: The issue type selected is invalid`;
Jira's "Move" wizard is a different, not-yet-exercised path). RHWA-1187 was closed as a
duplicate of this ticket.

## 2. Summary

With `StorageBasedRemediationConfig.spec.detectOnlyMode: Enabled`, the SBR agent substitutes
a no-op mock watchdog and never arms the real device. It must therefore start and stay Ready
even when `/dev/watchdog` is held open by another process. Only the watchdog portion of
`runPreflightChecks()` is skipped — the SBR shared-device check and node ID resolution must
still run.

## 3. Scope

- **In scope**:
  - Every agent pod of a `detectOnlyMode: Enabled` SBRC reaches Ready while a privileged
    keepalive pod holds `/dev/watchdog` open on every schedulable worker node. Agent pods stay
    Ready with the same identities and restart counts throughout the 90-second observation,
    and no worker reports `SBRStorageUnhealthy=True`.
- **Out of scope**:
  - Exact preflight log messages or proof of which internal preflight checks ran. This test
    verifies observable agent readiness and stability under watchdog contention.
  - A separate "watchdog device missing entirely" scenario. I checked `runPreflightChecks()`
    directly: when `detectOnlyMode` is `true`, `watchdogPath` is never read at all — the
    branch that would check it is skipped unconditionally. A busy device and a missing device
    hit the exact same code path, so a second scenario built around a nonexistent
    `watchdogFilePath` would duplicate this spec's coverage without catching any additional
    regression. Not implemented for that reason.
  - Everything else OCP-88876 already proves about the `detectOnlyMode` field — spec
    reflection, storage-fault suppression, the Enabled/Disabled toggle, DaemonSet GC. This
    document does not restate those; see section 12 for why this stays a sibling spec.
  - Watchdog behavior when `detectOnlyMode` is `Disabled`, where a busy device is a
    legitimate startup failure.
  - Whether a hardware/softdog watchdog exists on a node at all (OCP-88878).
  - Any fencing or remediation outcome — detect-only mode suppresses fencing by definition.

### What this replaces

`detect_only.go` already had a spec for this exact behavior, attributed to RHWA-1068:

```go
It("RHWA-1068 regression: agent pods reach Ready despite /dev/watchdog held by another process", ...)
```

I verified its state directly rather than assuming:

| Problem | Verified |
| ------- | -------- |
| Gated behind `if os.Getenv("SBR_TEST_RHWA1068") != "true" { Skip(...) }`, both for the spec and for the `BeforeAll` keepalive-pod creation. | `SBR_TEST_RHWA1068` is not set anywhere in this repo's CI config — no workflow, script, or job definition references it. The spec always skipped. |
| Comment claimed the bug "is not yet fixed in the current operator version." | Still present as of the file's last edit (2026-10-12), four months after the fix merged into `sbr-operator` (`medik8s/storage-based-remediation#65`, merged 2026-06-22). RHWA-1184 being `ON_QA` means the gate's premise no longer held. |
| Attributed only to RHWA-1068, which is `Closed`. | RHWA-1184 (the open, trackable 5.0 bug) had no spec attributed to it, and no `reportxml.ID` existed on the `It` at all. |
| No assertion that non-watchdog preflight checks still run. | A regression that skipped all of preflight in detect-only mode, not just the watchdog portion, would have passed undetected. |

This spec is reworked in place to fix all four: the gate is removed, `reportxml.ID("1933")` is
added, the positive preflight log lines are asserted (not just the absence of the crash
message), and a restart-count check is added so a pod that crashed and then recovered no
longer passes silently.

## 5. Preconditions

Asserted in `BeforeAll`:

1. The SBR operator deployment is Ready.
2. An RWX StorageClass is discoverable, or `SBR_STORAGE_CLASS` names one; otherwise skip.
3. At least two schedulable worker nodes exist.
4. Self Node Remediation is **not** required to be installed. SNR is the real-world holder of
   `/dev/watchdog` this bug was reported against, but the test creates its own keepalive pods,
   so it must not depend on — or skip for — SNR's presence or absence.
5. Any `test-sbrc-detect-only` SBRC left over from a prior run is deleted and confirmed fully
   gone before a fresh one is created.
6. A privileged keepalive pod is Running on every schedulable worker node. Failure to create
   or start a keepalive pod on any worker fails `BeforeAll`; partial watchdog contention is
   not accepted.
7. The `detectOnlyMode: Enabled` SBRC is created only after the keepalive pods are Running,
   so agents meet a busy watchdog on their first start rather than after a later restart.

## 6. Test steps

| # | Step (`By` text) | Expected result |
| - | ---------------- | ---------------- |
| 1 | Creating watchdog-keepalive pods on all worker nodes (RHWA-1184 precondition) | A keepalive pod is Running and holds `/dev/watchdog` open on every schedulable worker |
| 2 | Asserting ALL agent DaemonSet pods are Ready — none should be in CrashLoopBackOff | `NumberReady == DesiredNumberScheduled` for `sbr-agent-test-sbrc-detect-only` within `sbrparams.DetectOnlyAllPodsReadyTimeout` |
| 3 | Recording agent pod identities and restart counts before the observation window | Every desired agent pod is present and Running; each container's `restartCount` is `0`, and pod UIDs are recorded |
| 4 | Consistently asserting agent and keepalive health and no worker `SBRStorageUnhealthy=True` for `<duration>` while the watchdog is held | For `sbrparams.DetectOnlySuppressionCheckDuration`, every agent pod remains Ready with its recorded UID and restart counts; every keepalive container remains running without restarts; no worker reports `SBRStorageUnhealthy=True` |
| 5 | DeferCleanup: deleting watchdog-keepalive pods to release /dev/watchdog | Deletion is requested for every keepalive pod so the watchdog handle is released on termination |

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1933")` runs and passes, with no `Skip`.
- With `/dev/watchdog` held open on every worker node, all `sbr-agent-test-sbrc-detect-only`
  pods reach Ready within `sbrparams.DetectOnlyAllPodsReadyTimeout` and remain Ready with the
  same UIDs and container restart counts throughout `sbrparams.DetectOnlySuppressionCheckDuration`.
- Every watchdog keepalive container remains running without restarts throughout the same
  observation, and no worker reports `SBRStorageUnhealthy=True`.
- Cleanup runs: keepalive pod deletion is requested, and `AfterAll` waits for the detect-only
  SBRC to be removed.

On a build without the RHWA-1184 fix, this spec fails at step 2: every agent exits on the
watchdog preflight error and `NumberReady` stays `0` until the timeout — the regression this
test case exists to catch.

## 9. Cleanup

- `DeferCleanup` deletes the watchdog-keepalive pods; the keepalive command writes the
  magic-close character before releasing the device, so cleanup never resets the node.
  Deletion tolerates a pod that is already gone and logs via `GinkgoT().Logf` rather than
  failing.
- `AfterAll` removes the `test-sbrc-detect-only` SBRC, waits for it to be fully gone
  (tolerating `IsNotFound`), and removes any remaining keepalive pods as a second net.
- `BeforeAll` requires a keepalive pod on every schedulable worker. A creation or startup
  failure on any worker fails setup; partial watchdog contention is not accepted.

## 12. Implementation sketch

Implemented in `tests/sbr-operator/tests/detect_only.go`:

- `BeforeAll` creates the keepalive pods unconditionally; the `os.Getenv("SBR_TEST_RHWA1068")`
  branch and its paired "skipping watchdog-keepalive pods" log line are removed, along with the
  now-unused `os` import.
- Keepalive creation fails the setup if any worker pod cannot start. The command checks that
  opening `/dev/watchdog` and each keepalive write succeeds, pings with `.`, and writes the
  magic-close character `V` when it exits.
- The `It` is renamed to reference RHWA-1184, carries `reportxml.ID("1933")`, and its `Skip`
  on the missing env var is removed.
- `labels.ComponentController` is replaced with `labels.ComponentDaemonSet`.
- The test records agent pod UIDs and container restart counts, then checks pod readiness,
  identity, restart counts, keepalive process state, and node conditions during the full
  observation window. It does not infer health from logs.

### Why this stays a sibling spec rather than folding into OCP-88876

Both specs live in the same `Ordered` container, so the keepalive precondition in `BeforeAll`
is shared either way. They stay separate `It`s because:

- OCP-88876's subject is the `detectOnlyMode` field itself — reflection, fault suppression,
  toggle, GC. This spec's subject is agent startup with a busy watchdog. One failure each is
  diagnostic; a merged spec would report a single failure for two unrelated regressions.
- OCP-88876 carries an existing Polarion ID and run history; changing its assertions breaks
  comparability with prior runs, while a sibling spec with its own `reportxml.ID` does not.
