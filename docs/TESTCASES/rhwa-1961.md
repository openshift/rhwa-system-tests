This is the Block-mode counterpart of the Filesystem detection-only test
(`tests/sbr-operator/tests/detect_only.go`, OCP-88742). It carries its own
`reportxml.ID("1961")` rather than sharing that ID, so the two runs report as
distinct results — the same pattern the block node hang test (RHWA-1931), the
block split-brain test (RHWA-1934), the block total storage I/O loss test
(RHWA-1944) and the block SBRC lifecycle test (RHWA-1960) follow.

It is also a deliberately stronger test than its Filesystem counterpart. OCP-88742
injects a storage fault and asserts that no remediation CR ever appears; this spec
puts a remediation CR in place on purpose — twice, once per reboot route — and
asserts the node survives it.

## 2. Summary

Runs a `StorageBasedRemediationConfig` with `sharedStorageVolumeMode: Block` and
`detectOnlyMode: Enabled` on a Ceph RBD StorageClass, and proves that SBR still
detects and reports an unhealthy node but never reboots one.

SBR reboots a node by exactly two routes, and both open only once a
`StorageBasedRemediation` CR exists for it:

1. a peer writes a fence message into the victim's fence slot and the victim reads
   it off its own slot and self-fences;
2. the victim's own agent sees a CR for itself, stops petting `/dev/watchdog`, and
   the watchdog reboots the node.

The spec walks into both in turn — with the fence message confirmed on the device
for the first, and the victim's storage cut off entirely for the second — and
asserts the node stays up and Ready each time. It also asserts the positive half
of detect-only mode: `SBRStorageUnhealthy=True` is still set, NHC still creates a
CR, and the agent emits an `SBRUnhealthyDetectOnly` Warning in place of disarming
its watchdog.

## 3. Scope

- **In scope**: detect-only behaviour on a Block-mode SBRC backed by Ceph RBD —
  the victim ignoring a live fence message sitting in its own fence slot; the
  victim's watchdog never firing when its storage is gone and a CR exists for it;
  `SBRStorageUnhealthy=True` (reason `HeartbeatTimeout`) still being set by a peer;
  NHC still creating a `StorageBasedRemediation` CR; the `SBRUnhealthyDetectOnly`
  Warning being emitted on the SBRC and naming the victim; and the node being
  uncordoned with no out-of-service taint once the hand-made CR is deleted.
- **Out of scope**:
  - The same behaviour on RWX **Filesystem** storage (`detect_only.go`,
    OCP-88742), including its `detectOnlyMode` toggle (Enabled → Disabled →
    Enabled) and the DaemonSet garbage-collection check on delete.
  - RHWA-1068 (agent startup with `/dev/watchdog` already held). That is a
    separate planned Block-mode spec, "Detection-Only Mode with /dev/watchdog
    held", and is not covered here.
  - Whether the out-of-service taint should be applied to a live node in
    detect-only mode. The reconciler ignores `detectOnlyMode` (RHWA-1877); the
    spec **records** the taint when it sees it but does not fail on it. See
    §8.
  - Fencing that is supposed to reboot the node — `block_storage_total_loss.go`
    (RHWA-1944) covers the watchdog path with detect-only **off**, and
    `block_storage_split_brain.go` (RHWA-1934) covers the fence-read path.
  - The on-disk layout of the block device (`block_storage_inspection.go`,
    RHWA-1926) and the Block-mode SBRC lifecycle (`block_storage_sbrc_lifecycle.go`,
    RHWA-1960).

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator

# Optional:
```

- `SBR_RBD_STORAGE_CLASS` — the Ceph RBD StorageClass to use. When unset, a
  StorageClass whose provisioner contains `rbd.csi.ceph.com` is auto-discovered;
  the spec **skips** when the cluster has none.
- `SBR_INJECTOR_IMAGE` — the image for the privileged injector pod. It must
  provide `nsenter` and `iptables`; `ubi-minimal` has neither.

## 5. Preconditions

1. The installed SBR CRD ships `spec.sharedStorageVolumeMode`
   (`requireSBRCBlockVolumeModeSupport`). Below `FirstSBRCsvWithBlockVolumeMode`
   (`5.8.0`) the spec skips; at or above it a missing field fails the suite, and an
   unknown CSV version fails rather than skipping a capable operator.
2. The `NodeHealthCheck` CRD is installed; otherwise the spec skips. The second
   half needs NHC to create the remediation CR the way production would.
3. No `NodeHealthCheck` other than this spec's own already remediates through the
   SBR template (`requireNoSBRNodeHealthCheck`); otherwise the spec skips. The
   first half owns the only `StorageBasedRemediation` CR there is — a foreign NHC
   creating its own would make "the victim stayed up" unattributable. This spec's
   own leftover NHC (`nhc-sbr-block-detect-only`) is deleted and waited out first,
   so a crashed prior run does not skip the spec.
4. Self Node Remediation is not running (`failIfSNRRunning`). Detect-only mode
   never arms the watchdog, but the check is shared with every other Block-mode
   setup path and keeps the spec's environment identical to theirs.
5. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one; otherwise
   the spec skips.
6. A schedulable worker node that hosts no SBR controller pod is available
   (`pickTargetWorkerNode`); otherwise the spec skips.
7. `iptables` is usable in that node's host namespaces. Probed with a short-lived
   host-command pod before anything is created: on an nftables-only node without
   the compatibility layer the second half's fault cannot be injected at all,
   which is a skip rather than a failure.
8. No SBRC named `test-sbrc-block-detect-only` is left over from a prior run — it
   is deleted and waited out in `BeforeAll`.
9. After the SBRC comes up, `status.storageValidation.concurrentWriteable` is
   `true`. Without it the reconciler withholds fencing, no fence message is ever
   written, and the first half would pass without testing anything.

## 6. Test steps

Steps 1–6 are `BeforeAll` (see §5); steps 18–22 are `AfterAll` (see §9).

| #   | Step (`By` text)                                                                                 | Expected result                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 7   | Step 7: Recording the victim's boot-id before any remediation                                       | The victim's boot-id is read and logged                                                                                  |
| 8   | Step 8: Creating a StorageBasedRemediation CR for the victim node                                   | A CR named after the victim is created by the test, not by NHC — the victim's storage is healthy, so nothing would flag it |
| 9   | Step 9: Waiting for a peer to write the fence message into the victim's own fence slot              | Read through the observer agent on another node: fence slot index `nodeID-1` holds a fence message with a non-NONE reason and `TargetNodeID` equal to the victim's node ID |
| 10  | Step 10: Consistently asserting for 90s that the victim ignores the fence it can read               | The victim keeps the same boot-id and stays `Ready` for the whole window                                                 |
| 11  | Step 11: Deleting the StorageBasedRemediation CR and waiting for the victim to be schedulable again | The CR is deleted; the agent finalizer uncordons the node and the out-of-service taint (if any) is removed              |
| 12  | Step 12: Creating the NodeHealthCheck that remediates SBRStorageUnhealthy nodes through SBR         | The SBR template exists (created here when missing) and an NHC with `maxUnhealthy: 1` on `SBRStorageUnhealthy=True` is created. `SBRStorageUnhealthy` is asserted not-True on the victim and its boot-id is re-read |
| 13  | Step 13: Starting a privileged injector pod that blocks Ceph traffic in both directions             | REJECT rules for ports 3300, 6789 and 6800–7300 are inserted on both the OUTPUT and the INPUT chain of the victim's host, with no time limit |
| 14  | Step 14: Waiting for SBRStorageUnhealthy=True (reason HeartbeatTimeout) on the victim node          | A peer reads the victim's silent heartbeat slot off the device and sets the condition — detection still works in detect-only mode |
| 15  | Step 15: Waiting for NHC to create a StorageBasedRemediation CR for the victim node                 | NHC creates the CR. The no-reboot window of step 17 is counted from this moment                                          |
| 16  | Step 16: Waiting for an SBRUnhealthyDetectOnly Warning on the SBRC naming the victim node           | A Warning with reason `SBRUnhealthyDetectOnly`, recorded against the SBRC and whose message contains the victim's node name, is emitted — the agent reached the watchdog tick and chose not to disarm |
| 17  | Step 17: Consistently asserting for the remainder of the no-reboot window that the victim is never rebooted by its watchdog | The victim stays `Ready` on the same boot-id for the whole window; one final boot-id read after the window confirms it   |

The spec runs `ContinueOnFailure`, so a failed assertion reports and the remaining
steps still run.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1961")` runs and passes.
- The SBRC comes up in Block mode with `detectOnlyMode: Enabled`: its device-init
  Job succeeds, its agent DaemonSet becomes Ready within `SBRCReadyTimeout` (10m),
  and `status.storageValidation.concurrentWriteable` is `true` within
  `StorageInjectionTimeout` (3m). Agents reaching **Ready**, not merely Running, is
  itself part of the result: readiness is gated on the preflight-ok file, so it
  means the Block write test passed with the watchdog check skipped.
- **Fence-read path.** Within `BlockFenceMessageTimeout` (3m) of the hand-made CR,
  the victim's own fence slot (index `nodeID-1` of the fence region, read off the
  device through an agent on another node) holds a fence message with a non-NONE
  reason targeting the victim's node ID. For `DetectOnlySuppressionCheckDuration`
  (90s) afterwards the victim keeps that boot-id and stays `Ready`.
- Deleting the hand-made CR leaves the victim schedulable with no
  `node.kubernetes.io/out-of-service` taint within `SBRCRCleanupTimeout` (10m).
- **Detection.** With Ceph blocked in both directions, the victim reaches
  `SBRStorageUnhealthy=True` with reason `HeartbeatTimeout` within
  `StorageInjectionTimeout` (3m), set by a peer reading the device.
- **Watchdog path.** NHC creates a `StorageBasedRemediation` CR within
  `NHCSBRCRCreationTimeout` (5m); an `SBRUnhealthyDetectOnly` **Warning** is
  recorded against the SBRC with the victim's node name in its message within
  `StorageInjectionTimeout` (3m); and for the rest of
  `BlockDetectOnlyNoRebootWindow` (10m from the CR appearing, floored at
  `BlockDetectOnlyNoRebootMinWindow`, 2m) the victim stays `Ready` on the same
  boot-id. A final boot-id read after the window closes still matches.
- Cleanup finishes: no `nhc-sbr-block-detect-only` NHC, no
  `StorageBasedRemediation` for the victim, no `test-sbrc-block-detect-only` SBRC
  and no injector pod remain; the victim is uncordoned and its Ceph REJECT rules
  are flushed.

## 8. Failure / known issues

- **RHWA-1877 — the remediation reconciler ignores `detectOnlyMode`.** Peer agents
  cordon the victim and write a fence message regardless of the mode, and once the
  victim's heartbeat goes stale in the second half they prove its death from
  storage and apply the `node.kubernetes.io/out-of-service` taint to a node that is
  still alive. The spec **records** this as the report entry
  `sbr-block-detect-only-oos-taint` and logs it, but does not fail on it: whether a
  live node being tainted is a bug to fail a detect-only run is a product decision,
  and the spec passes on what it set out to measure — that nothing rebooted.
  Revisit this once RHWA-1877 is resolved.
- **RHWA-1876 — SBR as an NHC remediator while `detectOnlyMode` is Enabled is a
  misconfiguration.** This spec does it deliberately, because it is the only way to
  get a remediation CR in front of the victim's own agent and prove the watchdog
  stays armed-off. It is confined to this spec's own NHC, which is created in
  step 12 and removed in teardown.
- **FencingFailed events during step 10 are expected.** The victim's heartbeat stays
  fresh throughout the first half, so its death is never proven: the reconciler's
  60s monitor window expires, it emits `FencingFailed`, rewrites the fence and
  restarts the window. That is the correct behaviour of a fence nobody acts on.
- **Step 17's window is generous on purpose.** It is sized as a watchdog firing
  (`BlockDetectOnlyWatchdogFireAllowance`, 2m) plus a full bare-metal reboot
  (`BlockDetectOnlyRebootAllowance`, 8m), counted from the CR appearing rather than
  from the event, so a slow node cannot outlast it. In practice the `Ready`
  assertion catches a reboot within a minute or two of the watchdog firing — a node
  on its way down loses `Ready` long before its boot-id moves — so most of the
  window is margin.
- **The `SBRUnhealthyDetectOnly` event is matched by message, not by object.** The
  agent records it against the `StorageBasedRemediationConfig` it runs under (its
  `recorderObject`), not against the Node or its own Pod, and the node name and ID
  appear only in the message text. Every agent shares that involved object, so
  without the message match another node's event would satisfy the wait.
  If `--sbr-config-name` is unset the agent falls back to the first SBRC in its
  namespace, which is this spec's SBRC because it pre-cleans and is the only one
  running — but the UID filter means a different SBRC would fail the step rather
  than pass it silently.

## 9. Cleanup

`AfterAll` runs in dependency order, not creation order, because each step unblocks
the next:

1. **Lift the storage block** — delete the injector pod and run a flush pod that
   removes any leftover Ceph REJECT rule. Until this happens the victim's
   remediation is still in flight, the NHC validating webhook refuses the NHC's
   deletion, and the remediation CR will not drain.
2. **Delete the NodeHealthCheck** (`cleanupNHCCR`, retried up to
   `NHCCleanupTimeout`, 5m). A CR still present afterwards is recorded as the report
   entry `sbr-nhc-cleanup-failed`.
3. **Delete the remediation CR** the ordinary way first
   (`helpers.DeleteRemediationCR`). With the NHC gone and storage back, the agent
   finalizer drains on its own and undoes the cordon and the out-of-service taint it
   applied. Force-stripping finalizers (`cleanupSBRCR`) is the fallback only, and
   matters here because the CR at this point is usually NHC's, not the one the test
   wrote.
4. **Uncordon the victim** if anything left it cordoned.
5. **Delete the SBRC** and wait for it to be gone.
6. **Delete the StorageBasedRemediationTemplate**, but only when this spec created
   it. It goes last because both the NHC and the remediation CR still reference it
   on the way out. The spec uses `createSBRTemplateIfMissing` rather than
   `ensureSBRTemplate` precisely so teardown owns the ordering instead of a
   `DeferCleanup` firing in registration order.

`BeforeAll` pre-cleans this spec's NHC and SBRC from a prior run. All deletes
tolerate `IsNotFound`, and teardown failures are logged with `GinkgoWriter.Printf`
rather than failing the suite, so cleanup never masks the test result.

## 12. Implementation sketch

Implemented in
[`tests/sbr-operator/tests/block_storage_detect_only.go`](../../tests/sbr-operator/tests/block_storage_detect_only.go)
(`It("Detection-only mode: a Ceph RBD block-mode node is reported unhealthy and fenced on storage, but never rebooted", reportxml.ID("1961"), …)`).

Helpers it adds, all in the shared Block-mode helper files:

- `blockNodeIDOf` — looks a node's SBR node ID up in the on-device node map.
  `victimHeartbeatSlotState` now uses it too.
- `liveFenceMessageFor` — returns the fence message standing in a node's own fence
  slot, erroring on an empty slot, a retracted (reason-NONE) fence, or a fence
  aimed at a different node ID.
- `createBlockModeSBRCAndWaitReady` — extracted from `setupBlockModeNHCScenario`,
  which now calls it, so a spec can bring up a Block-mode SBRC with a custom spec
  and no NodeHealthCheck.
- `createSBRTemplateIfMissing` / `deleteSBRTemplate` — split out of
  `ensureSBRTemplate`, which now calls them, so a caller can own the template's
  deletion order.
