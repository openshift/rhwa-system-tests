# RHWA-1917 — SBR agents on Ceph RBD report no device I/O errors and no false unhealthy condition while every worker is under CPU and I/O load

## 2. Summary

With a `StorageBasedRemediationConfig` on Ceph RBD block storage running at the
minimum `sbrTimeoutSeconds` (10s), the SBR agents must keep working while every
worker node is loaded with CPU and disk I/O: no device I/O errors are recorded,
and no node is marked `SBRStorageUnhealthy`. The point is to prove that node
load alone does not produce a false-positive fencing trigger when the heartbeat
timeout is at its tightest.

## 3. Scope

- **In scope**: an SBRC with `sharedStorageVolumeMode: Block`,
  `sbrTimeoutSeconds: 10`, `maxConsecutiveFailures: 3`; three sampling phases
  (baseline, under load, recovery) that scrape each agent's `/metrics` on port
  8082; `sbr_device_io_errors_total` staying at zero across all three phases;
  no worker node carrying the `SBRStorageUnhealthy` condition; a load
  DaemonSet that deploys on every worker and is fully cleaned up; a JSON
  report written to `ARTIFACT_DIR`.
- **Out of scope**:
  - **Heartbeat latency — despite the test's name.** The P99/max thresholds in
    `sbrparams` (500ms loaded, 100ms baseline, 1000ms absolute, 3x degradation)
    are coded but inert: the agent exposes no
    `sbr_heartbeat_write_duration_seconds` histogram, so `LatencySamples` is
    never populated, `SampleCount` stays 0, and every latency assertion is
    skipped at runtime (`block_storage_rbd_performance.go:237`, `:257-259`,
    `:294`, `:321-323`, and the note at `:218-224`). What remains is an I/O
    error and liveness check under load.
  - **Watchdog continuity as a gate.** Gaps in `sbr_watchdog_pets_total` — the
    stand-in for a heartbeat sequence number — are logged as warnings only and
    never fail the spec (`:266-277`).
  - **Load on the shared block device.** The I/O workers `dd` into the stress
    container's own `/tmp`, not the RBD device backing the heartbeat, so the
    device itself is not the thing being stressed.
  - **Fencing behaviour under load.** No `StorageBasedRemediation` CR is
    created; fencing on RBD is covered by `block_storage_rbd.go` (RHWA-1916)
    and storage-loss detection by `storage_loss_watchdog.go`.

## 4. Environment

| Requirement  | Value                                                                                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Cluster      | At least 2 worker nodes with SBR agent pods Running — asserted, the spec fails below that                                    |
| Topology     | any (the spec sets no topology label)                                                                                       |
| Platform     | any (`platform:any`)                                                                                                        |
| Storage      | A Ceph RBD **block** StorageClass (provisioner containing `rbd.csi.ceph.com`), used with `sharedStorageVolumeMode: Block`   |
| Network      | connected — the load pods pull `registry.fedoraproject.org/fedora:latest`, which is hardcoded with no env override          |
| Namespace    | `openshift-workload-availability` (`medik8sparams.OperatorNs`)                                                              |
| Destructive? | no — labelled `DisruptionNonDestructive`; no node is fenced, rebooted, or cordoned. It does load every worker for the duration of the run and creates a cluster-scoped `ClusterRoleBinding` granting the privileged SCC |

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator
export SBR_RBD_STORAGE_CLASS=ocs-storagecluster-ceph-rbd   # optional
export ARTIFACT_DIR="$(mktemp -d)"                         # optional
```

`SBR_RBD_STORAGE_CLASS` names the Ceph RBD StorageClass. Unset is the normal
case: the test auto-discovers the first StorageClass whose provisioner contains
`rbd.csi.ceph.com`, and `Skip`s with "No Ceph RBD StorageClass found; install
ODF or set SBR_RBD_STORAGE_CLASS env var" when there is none.

`ARTIFACT_DIR` is where the JSON performance report is written; unset, it
defaults to `/tmp/sbr-test-artifacts`, which the test creates. In Prow this is
already set, so the report lands with the other artifacts.

## 5. Preconditions

1. SBR operator installed in `openshift-workload-availability` with its
   controller running.
2. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one;
   otherwise the suite skips.
3. `BeforeAll` deletes any `StorageBasedRemediationConfig/test-sbrc-block-perf`
   left by an earlier run and waits for it to be fully gone before the spec
   creates its own.
4. The SBRC is created with the discovered class, `sharedStorageVolumeMode:
   Block`, `sbrTimeoutSeconds: 10` (the CRD minimum, for maximum stress) and
   `maxConsecutiveFailures: 3`, and its agent DaemonSet reaches full readiness
   (`waitForSBRCReady`).
5. At least two agent pods are Running; the spec asserts this before sampling.

## 6. Test steps

| #  | Step (`By` text)                                                | Expected result                                                                                                       |
| -- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1  | `Discovering Ceph RBD block storage class`                       | A Ceph RBD StorageClass name is resolved, or the spec skips                                                             |
| 2  | `Creating SBRC with Ceph RBD and minimum timeout for maximum stress` | SBRC `test-sbrc-block-perf` admitted with Block mode, `sbrTimeoutSeconds: 10`, `maxConsecutiveFailures: 3`           |
| 3  | `Waiting for agent DaemonSet to reach ready state`               | All agent pods for that SBRC are Ready; at least 2 are Running                                                          |
| 4  | `Monitoring baseline heartbeat latency for 2m0s`                 | Metrics scraped from every agent every 5s; phase ends after 5 successful rounds from all pods, or 2m, whichever is first |
| 5  | `Deploying stress-ng pods on all worker nodes`                   | ServiceAccount, privileged `ClusterRoleBinding`, and DaemonSet `sbr-perf-stressor` created; at least one pod scheduled  |
| 6  | `Waiting for stress pods to reach Running state`                 | The count of Running load pods is recorded (partial scheduling is tolerated and logged)                                 |
| 7  | `Monitoring heartbeat latency under load for 5m0s`               | Same sampling, with 4 CPU hashing workers and 2 `dd` I/O workers per node active                                        |
| 8  | `Removing stress pods and monitoring recovery`                   | DaemonSet, `ClusterRoleBinding`, and ServiceAccount deleted; all load pods terminate within 2m                          |
| 9  | `Monitoring heartbeat latency during recovery for 2m0s`          | Same sampling after the load is gone                                                                                    |
| 10 | `Validating heartbeat latency remains within acceptable bounds`  | Sub-steps: I/O error counts logged; watchdog continuity logged (warnings only); **total device I/O errors must be 0**. Latency sub-steps are skipped while the agent exposes no histogram |
| 11 | `Verifying no false-positive SBRStorageUnhealthy conditions`     | No worker node has the `SBRStorageUnhealthy` condition                                                                  |
| 12 | `Generating performance report`                                  | JSON report written under `ARTIFACT_DIR` and its path logged                                                            |

Each monitoring phase stops early once it has 5 successful sampling rounds from
every agent pod, so at a 5s poll interval the phases usually take about 25-30s
rather than the 2m/5m/2m the step names quote.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1917")` runs and passes.
- At least 2 agent pods are Running before sampling begins, and at least one
  load pod is deployed.
- `sbr_device_io_errors_total` summed over the baseline, loaded, and recovery
  phases is exactly 0.
- No worker node reports the `SBRStorageUnhealthy` condition at the end of the
  run — the false-positive check this test exists for.
- A JSON report is written under `ARTIFACT_DIR`.
- Cleanup finishes: the SBRC, the `sbr-perf-stressor` DaemonSet, its
  ServiceAccount, and the privileged `ClusterRoleBinding` are all gone.

While the agent exposes no latency histogram, the P99/max/degradation criteria
in section 3 are not evaluated — a green run does not mean latency was measured.

## 8. Failure / known issues

No open product bug gates this spec, so it carries no env var skip-gate.

Test-side gaps, tracked against this ticket:

| Gap                                                                           | Effect                                                                                     |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `reportxml.ID("TBD")` at `block_storage_rbd_performance.go:77`, and `TestID: "TBD"` in the report at `block_storage_rbd_performance_metrics_simple.go:399` | Results cannot be attributed to RHWA-1917; both must become `1917` before the status moves to `implemented` |
| No `tier:` or `component:` label on the `It`                                  | Mandatory per [AGENTS.md](AGENTS.md); CI selects with expressions such as `operator:sbr && tier:acceptance`, so this spec is silently skipped by those runs |
| `time.Sleep(10 * time.Second)` at `:164` and `:184`                           | The repository forbids `time.Sleep` in specs; both waits should be `Eventually` on an observable condition |
| Load image `registry.fedoraproject.org/fedora:latest` is hardcoded            | The spec cannot run on a disconnected cluster; the suite's other images take an env override such as `SBR_INJECTOR_IMAGE` |
| Jira RHWA-1917 is titled "SBR blcok perf test" and carries no label           | Fails `make check-testcase-jira`: the ticket must be titled `TEST: …` and labelled `rhwa-test` |

## 9. Cleanup

- `DeferCleanup` removes the SBRC, and removes the load DaemonSet together with
  its `ClusterRoleBinding` and ServiceAccount when any load pod was deployed.
- The load teardown also runs inline at step 8, so the `DeferCleanup` copy is
  the safety net for a failure between deployment and step 8.
- `AfterAll` deletes the SBRC again, tolerating `IsNotFound`.
- `BeforeAll` additionally clears a stale SBRC from a previous run and waits for
  it to disappear before creating a new one.
- Deletion failures during load teardown are logged with `GinkgoWriter.Printf`
  rather than failing the suite.
