# RHWA-1994 — the RHWA must-gather image collects every medik8s CRD and every live custom resource

## 1. Metadata

| Field                        | Value                                                   |
| ---------------------------- | ------------------------------------------------------- |
| Jira                         | [RHWA-1994](https://issues.redhat.com/browse/RHWA-1994) |
| `reportxml.ID`               | `1994`                                                  |
| Polarion (legacy) — OPTIONAL | None                                                    |
| Operators                    | FAR, MDR, NHC, NMO, SNR, SBR — all six; validated against v5.8.0 |
| Suite                        | `tests/medik8s-collection`                              |
| Spec file                    | `tests/medik8s-collection/tests/crd_collection.go`      |
| Author                       | whayutin                                                |
| Status                       | implemented                                             |

All four specs in this document share `reportxml.ID("1994")`: they are four
tiers of one behaviour — broad non-destructive coverage, SBR coverage,
maintenance coverage and remediation coverage — tracked by a single ticket.
Split the ID if the tiers ever need to be reported separately.

## 2. Summary

Configures every RHWA operator by creating a custom resource for each medik8s
CRD that can be instantiated safely, runs the RHWA must-gather image, and
requires the collected output to contain a file for every medik8s CRD
definition and every live custom resource on the cluster. Two of the
remediation CRDs are instantiated against a node that does not exist, which
yields a real collectable resource without remediating anything. Two further
specs repeat the comparison while a node is under `NodeMaintenance` and while
a `SelfNodeRemediation` is active, so the remediation-time CRs are covered
too. Every collection is published as a tar.gz artifact, and each logs which
image it actually pulled.

## 3. Scope

All six RHWA operators are exercised. Every CRD's **definition** is always
required to be collected; the table below is about whether a live **instance**
of it exists when the collection runs, which is the stronger check and the
thing the fixtures exist to arrange.

| Operator | CRD | Live instance | Created by |
| -------- | --- | ------------- | ---------- |
| FAR | `fenceagentsremediationtemplates` | yes | spec 1 fixture |
| FAR | `fenceagentsremediations` | no | — fences a node |
| MDR | `machinedeletionremediationtemplates` | yes | spec 1 fixture |
| MDR | `machinedeletionremediations` | yes | spec 1 fixture, named after an absent node |
| NHC | `nodehealthchecks` | yes | spec 1 fixture |
| NMO | `nodemaintenances` | yes | spec 3 (destructive) |
| SNR | `selfnoderemediationtemplates` | yes | spec 1 fixture |
| SNR | `selfnoderemediationconfigs` | yes | the operator's own default config |
| SNR | `selfnoderemediations` | yes | spec 4 (destructive) |
| SBR | `storagebasedremediationtemplates` | yes | spec 1 fixture |
| SBR | `storagebasedremediationconfigs` | yes | spec 2 fixture, no shared storage so it stays inert |
| SBR | `storagebasedremediations` | yes | spec 1 and spec 2 fixtures, absent node |

Eleven of the twelve CRDs have a live instance — every one except
`fenceagentsremediations`. Spec 1 covers five operators, spec 2 completes SBR
by adding its config, and specs 3 and 4 add the two CRDs that cannot exist
without disrupting a node.

- **In scope**: that the collection script in
  [medik8s/must-gather](https://github.com/medik8s/must-gather) misses nothing.
  The expected result is read from the cluster with the same rule the script
  selects by (a CRD name containing `medik8s`), so the comparison covers CRDs
  added by future operator releases without a code change. Also covered: the
  `version` file the script writes itself, node YAML for every node, and the
  operator namespace's workloads and per-pod log directories.
- **Out of scope**:
  - *Whether the collected YAML is correct or complete in content.* This test
    asserts a file exists per resource, not what is inside it.
  - *Instances of `fenceagentsremediations`.* FAR needs real BMC credentials
    and taints the node before it attempts to fence, so even a CR that can
    never succeed leaves state behind to clean up. Its CRD **definition** is
    still required to be collected.
  - *A storage-backed `StorageBasedRemediationConfig`.* Spec 2 creates a
    config that deliberately omits `sharedStorageClass`, so the controller
    reconciles and owns it but creates no agent DaemonSet and no PVC. A
    config wired to real RWX storage, with agents running on real nodes, is
    the SBR suite's territory.
  - *Whether MDR actually deletes a `Machine`.* Its fixture is named after a
    node that does not exist, so the controller declines with
    `RemediationCannotStartNodeNotFound`. That proves the CR was reconciled
    and is collectable; it proves nothing about the deletion path, which the
    MDR suite covers.
  - *Whether SBR remediates anything at all.* Its remediation CR stays inert
    even in spec 2, where a config is present: without shared storage the
    remediation path never engages, so the CR takes no finalizer and reports
    no status. It is a real instance of its CRD for the collection to find,
    and nothing more. The SBR suite covers the remediation path.
  - *Per-operator must-gather assertions.* `tests/nhc-operator/tests/must_gather.go`
    covers NHC data during active remediation; the MDR, NMO, SBR and SNR suites
    each have their own `must_gather.go`. This test asks only whether anything
    was missed overall.
  - *Remediation behaviour itself.* The destructive specs create a
    `NodeMaintenance` or `SelfNodeRemediation` CR to have one to collect; they
    do not assert the remediation's outcome. `rhwa-1972` and the SNR suite
    cover that.

## 5. Preconditions

Asserted in `BeforeAll`:

1. Every CRD in `collectionparams.RequiredCRDNames` — all twelve installed by
   the six RHWA operators — is present. Missing any one fails the suite rather
   than quietly reducing what the cluster-derived expectation covers.
2. No node is named `collectionparams.AbsentNodeName`
   (`rhwa-collection-absent-node`). The `MachineDeletionRemediation` and
   `StorageBasedRemediation` fixtures are both named after it, and both
   operators identify their target by the CR's own name — MDR deletes that
   node's `Machine`, SBR storage-fences it — so a node by that name would
   mean the fixtures remediate a working node. Any read error other than
   `NotFound` also fails: absence that cannot be read is not absence.

Asserted per destructive spec, before anything is created:

3. At least `collectionparams.MinWorkersForDestructive` (3) Ready worker nodes
   exist, so one can be disrupted and the operators still have somewhere to
   run. Below that the spec `Skip`s with the count in the message, recorded as
   a `skipped-reason` report entry.

Stale fixtures from an interrupted run are tolerated rather than fatal:
`createFixtureObject` reuses an existing object on `IsAlreadyExists` and logs
that it did.

### Common to all four specs

Each of the four specs runs its own collection, so each of the following
happens once per spec rather than once per suite run.

### Artifacts

Every collection is published as one gzipped tar in the job's artifact
directory, so a run leaves behind the diagnostics it gathered and not just a
verdict. Each spec produces its own archive:

```text
rhwa-<operator acronyms>-must-gather-<UTC timestamp>.tar.gz
```

The acronyms name the operators whose custom resources are actually in that
collection, sorted, so the file says what it holds without being opened. They
differ per spec, which is also what tells the three archives apart:

```text
rhwa-far-mdr-nhc-sbr-snr-must-gather-20261029-222900.tar.gz   spec 1
rhwa-sbr-snr-must-gather-20261029-225626.tar.gz               spec 2
rhwa-nmo-snr-must-gather-20261029-223145.tar.gz               spec 3
rhwa-snr-must-gather-20261029-224012.tar.gz                   spec 4
```

They follow live custom resources, not installed CRDs: every operator's CRD
definition is collected on every run, so naming by those would give the same
name every time. A CRD added by a future operator falls back to the initials
of its API group.

The destination is `ARTIFACT_DIR`, falling back to `ECO_REPORTS_DUMP_DIR`,
falling back to `/tmp/rhwa-collection-artifacts`. There is no "nowhere to put
this" case: a collection is always kept, which matters most for the single
spec run by hand that configures nothing.

Archives accumulate. Nothing in the suite removes the artifact directory or
prunes what earlier runs put there — each collection only adds a file, and the
UTC timestamp in the name keeps runs from colliding. That is deliberate: it
lets a failing collection be compared against the last good one, and it means
a later suite never destroys an earlier suite's evidence. Pruning is a manual
decision.


Each archive holds the collected tree plus the `oc-adm-must-gather.log`, under
a single top-level directory named after the archive — `tar xzf
rhwa-snr-must-gather-20261029-224012.tar.gz` yields
`rhwa-snr-must-gather-20261029-224012/`. A collection of this cluster is about
5.5 MB raw and 0.5 MB compressed, so the archive is published rather than the
raw tree: an order of magnitude smaller, and the form a support case asks for.

Archiving happens **before** the collection's own error is asserted, so a
failed or partial gather is still published — that is the run whose output
someone will actually need. An archiving failure is reported as a
`must-gather-archive-failed` entry and never fails the spec; losing an
artifact must not turn a passing comparison into a failure or mask a real one.

### Image provenance

Each collection logs which image it ran, in four parts, because "the test
passed" is worthless without knowing which build produced the output:

1. The reference and where it came from — `MUST_GATHER_IMAGE` or the default.
2. The digest that reference resolves to now, from `oc image info`. The default
   is a floating `:latest`, so the digest is what makes a run reproducible.
3. The `Using must-gather plug-in image`, `namespace/… created` and `pod for
   plug-in image … created` lines echoed out of `oc adm must-gather`'s own
   output, which is otherwise a long file listing in the saved artifact.
4. The image each container of the gather pod **actually pulled**, read from
   `status.containerStatuses[].imageID` on the live pod, with the pod and node
   names. This is the only place an `ImageDigestMirrorSet` or
   `ImageContentSourcePolicy` redirect is visible; when the pulled registry
   differs from the requested one the report says so explicitly.

Part 4 is captured by a background watcher started before the collection,
because `oc adm must-gather` deletes its namespace as soon as it finishes —
after the run there is nothing left to ask. If the watcher misses the pod the
report says so and the spec still passes: this is provenance reporting, not an
assertion. The run log gets the full block; the JUnit artifact gets a one-line
`must-gather-image` report entry, `<requested> -> <pulled>`.

Example from a passing run:

```text
must-gather image provenance:
  requested image: quay.io/medik8s/must-gather:latest
  pod openshift-must-gather-knmvf/must-gather-7z7rn on node master-2
    container "copy"
      requested: quay.io/medik8s/must-gather:latest
      pulled:    quay.io/medik8s/must-gather@sha256:9d3dcb2e…
    container "gather"
      requested: quay.io/medik8s/must-gather:latest
      pulled:    quay.io/medik8s/must-gather@sha256:9d3dcb2e…
```

## 7. Pass criteria

- The four specs carrying `reportxml.ID("1994")` run and pass; on a cluster
  with fewer than three Ready workers the two destructive ones `Skip` with a
  recorded `skipped-reason`.
- Every CRD whose name contains `medik8s` has a definition at
  `cluster-scoped-resources/apiextensions.k8s.io/customresourcedefinitions/<plural.group>.yaml`,
  and all twelve `RequiredCRDNames` are among them.
- Every custom resource of those CRDs that was live when the inventory was
  taken has its own YAML: cluster-scoped at
  `cluster-scoped-resources/<group>/<plural>/<name>.yaml`, namespaced at
  `namespaces/<namespace>/<group>/<plural>/<name>.yaml`.
- The `version` file exists at the gather root. `oc adm inspect` does not write
  it, so its presence is what proves the collection script itself finished
  rather than exiting early.
- Node YAML exists for every node, and the operator namespace contributed its
  namespace YAML, `core/pods.yaml`, `apps/deployments.yaml` and a log directory
  per non-terminating pod.
- Nothing was remediated to achieve any of the above. Specifically: no node is
  named `rhwa-collection-absent-node`, and the `MachineDeletionRemediation`
  created for it reports `RemediationCannotStartNodeNotFound` — so its
  controller reconciled the CR and deleted no `Machine`.
- Each collection leaves an `rhwa-<acronyms>-must-gather-<timestamp>.tar.gz` in the artifact
  directory, recorded as a `must-gather-archive` report entry, and logs the
  image it pulled as a `must-gather-image` entry.
- Cleanup finishes: every fixture CR is gone, the disrupted node is Ready and
  uncordoned, and no `openshift-must-gather-*` namespace created by this run
  remains.

A passing run does **not** prove that FAR, SBR or MDR can remediate anything;
see the out-of-scope list in section 3 for what each fixture deliberately
does not exercise.

## 9. Cleanup

- `DeferCleanup`, registered per fixture as it is created, deletes each fixture
  CR and waits for it to be gone. Registration happens *before* the create call,
  so a fixture that fails part way through the list is still removed.
- `DeferCleanup` removes any `openshift-must-gather-*` namespace created after
  the spec started, via `mustgather.CleanupNamespaces`.
- Spec 2 waits for its node to be uncordoned after the `NodeMaintenance` CR is
  deleted; spec 3 registers its node-recovery wait before creating the
  `SelfNodeRemediation` CR, so a failure between creation and the gather still
  waits the reboot out.
- Cleanup never fails the suite: `deleteFixtureObject`, `waitForNodeSchedulable`
  and the recovery wait log a warning with `GinkgoWriter.Printf` and add a
  `fixture-cleanup-failed`, `uncordon-failed` or `node-recovery-failed` report
  entry, so a leak is visible in the JUnit artifact without turning a passed
  assertion into a failure.

## 11. Running it standalone

Non-destructive only — safe on any cluster with the operators installed:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export WORKLOAD_IMAGE=registry.access.redhat.com/ubi9/ubi-minimal:latest
ginkgo -v --label-filter='disruption:nondestructive' \
    --timeout=40m ./tests/medik8s-collection/...
```

Archives land in `/tmp/rhwa-collection-artifacts` with no further setup, and
the run prints each one's full path. Export `ARTIFACT_DIR` to put them
somewhere else; `make run-tests` does that for you, pointing
`ECO_REPORTS_DUMP_DIR` at `ARTIFACT_DIR` or `/tmp/reports`. The directory is
created if missing.

All four specs, including the two that disrupt a worker, reusing the exports
above:

```bash
ginkgo -v --timeout=90m ./tests/medik8s-collection/...
```

Watch the run, on Linux or on macOS with `brew install watch`:

```bash
watch -n 5 -d tools/watch/collection-watch.sh
```

macOS ships no `watch`, so the script refreshes itself instead:

```bash
tools/watch/collection-watch.sh --loop
```

| Block | Shows |
| ----- | ----- |
| `crd instances` | every medik8s CRD with its live instance count |
| `medik8s custom resources` | namespace, kind and name of each instance |
| `must-gather` | the transient `openshift-must-gather-*` namespace and its pod |
| `archives` | the collection tarballs published so far, with size and full path |
| `nodes` | name, `Ready`, cordon |
| `operator pods not Running` | anything in the operator namespace that is not `Running` |

What must change: the `crd instances` counts rise by seven as the fixtures are
created — six on a cluster that already has a `StorageBasedRemediationConfig`,
since the `StorageBasedRemediation` fixture is then skipped — and a must-gather
pod appears and reaches `Completed`. On spec 2 the target node goes
`CORDON=YES`; on spec 3 it goes `Ready=Unknown` and back.

What must **not** change: no count may drop while the must-gather pod is
`Running`. A CR that disappears mid-gather becomes a missing artifact, and the
comparison then fails with no indication of why. Record the counts before the
run — that is what the assertion actually compares against. For spec 3 also
record the target node's boot ID (`tools/watch/snr-watch.sh` shows it), since
that is what distinguishes a real reboot from a node that was briefly
unreachable.
