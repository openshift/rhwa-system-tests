## 2. Summary

The Workload Availability Operator replaces the seven separately installed medik8s operators
with one operator that installs the others as operands, switched on and off through the
`spec.components` block of a cluster-scoped `WorkloadAvailabilityConfig` singleton named
`cluster`. This test enables each of the six operands in turn, waits for WAO to report it
running and its manager Deployments to be ready, disables it again, and confirms the manager is
removed before moving on to the next.

## 3. Scope

- **In scope**: the install-and-remove contract of every operand, driven through
  `spec.components.<operand>.enabled` and observed through `status.components[]` and the
  operand's manager Deployments. One operand at a time, from a cluster where WAO manages
  nothing.
- **Out of scope**:
  - **What each operand does once running.** Remediation, fencing and maintenance behaviour
    belong to the per-operator suites (`tests/snr-operator`, `tests/far-operator`,
    `tests/nhc-operator`, `tests/mdr-operator`, `tests/nmo-operator`, `tests/sbr-operator`);
    this test only proves the operator starts and stops.
  - **Several operands enabled at once.** The helper
    (`helpers.SetWAOComponents`) patches any combination in one request, but this spec cycles
    them one at a time so a failure names a single operand. A combined-enable test is a
    separate case.
  - **Manager resource overrides.** `spec.components.<operand>.manager.resources` is left
    untouched; the spec asserts the packaged defaults are preserved only to the extent that a
    merge patch of `enabled` does not disturb them.
  - **Removing what an operand creates.** Agent DaemonSets, `SelfNodeRemediationConfig` and
    `NodeHealthCheck` CRs outlive a disable by design — see sections 6 and 9.
  - **Upgrade and OLM metadata** of WAO itself.

## 5. Preconditions

Asserted in `BeforeAll`, which fails rather than skips when any of them is unmet:

1. The `WorkloadAvailabilityConfig` singleton named `cluster` exists and is readable. WAO
   creates it on startup, so its absence means WAO is not installed.
2. Every one of the six operands has `spec.components.<operand>.enabled` false.
3. Every one of the six operands reports `status.components[].phase` exactly `Disabled`.
   `DisableIncomplete` fails the precondition: it means agents, configs or native CRs from an
   earlier run are still on the cluster, and the failure message lists them.
4. No Deployment other than `workload-availability-operator-controller-manager`, and no
   DaemonSet at all, exists in `openshift-workload-availability`. Bare pods are ignored, so an
   OLM bundle-unpack pod left in the namespace does not fail the run.

## 6. Test steps

| #  | Step (`By` text)                                                        | Expected result                                                                 |
| -- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1  | `Verifying the WorkloadAvailabilityConfig singleton exists`               | `cluster` is readable                                                            |
| 2  | `Verifying every operand is disabled before the run`                      | All six operands: `enabled` false and phase `Disabled`                           |
| 3  | `Verifying no medik8s operand workload is running in the operator namespace` | Only WAO's own manager Deployment is present; no DaemonSets                   |
| 4  | `Enabling operand <operand>`                                              | The merge patch sets `spec.components.<operand>.enabled` true                    |
| 5  | `Waiting for operand <operand> to report phase Available`                 | Phase reaches `Available` within `OperandAvailableTimeout` (5m)                  |
| 6  | `Verifying the <operand> manager Deployments are ready`                   | Every Deployment in `waoparams.OperandDeployments[operand]` exists and is ready   |
| 7  | `Disabling operand <operand>`                                             | The merge patch sets `spec.components.<operand>.enabled` false                   |
| 8  | `Waiting for operand <operand> to stop reporting a running manager`       | Phase reaches `Disabled` or `DisableIncomplete` within `OperandDisabledTimeout` (3m) |
| 9  | `Verifying the <operand> manager Deployments are gone`                    | Every Deployment of that operand returns `NotFound`                              |
| 10 | `DeferCleanup: disabling every operand`                                   | All six operands set back to disabled, failures logged not asserted              |

Steps 4–9 repeat for each operand, in the API's display order: `nodeHealthCheck`,
`selfNodeRemediation`, `storageBasedRemediation`, `nodeMaintenance`, `fenceAgentsRemediation`,
`machineDeletionRemediation`.

Step 8 accepts two phases because `Disabled` is not always the end state. WAO reports
`DisableIncomplete` when anything outlives the manager, which is an expected outcome rather
than a fault:

- `selfNodeRemediation` always ends there once it has been enabled. Starting it creates a
  default `SelfNodeRemediationConfig`, which owns the agent DaemonSet; disabling the component
  removes neither. The first run retained exactly these two:

  ```text
  apps/v1 DaemonSet openshift-workload-availability/self-node-remediation-ds
  self-node-remediation.medik8s.io/v1alpha1 SelfNodeRemediationConfig openshift-workload-availability/self-node-remediation-config
  ```

- `nodeHealthCheck` ends there only on a cluster that already has `NodeHealthCheck` CRs, which
  it counts as retained. It does not create one itself: on a cluster with none, it returns to
  `Disabled`, as it did on the first run.

Either way the manager Deployment is removed, which is what step 9 checks. Whatever is retained
is printed to the Ginkgo log.

Measured on the first run (OCP 4.21, 3 masters and 3 workers, operand images already cached):
164s for the whole spec, each operand reaching `Available` in 15–30s and its disable confirmed
within 5s. The timeouts in section 7 are budgets for a cold image pull, not expected durations.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("2040")` runs and passes.
- For each of the six operands, in order: phase `Available` within
  `waoparams.OperandAvailableTimeout`, every Deployment named in
  `waoparams.OperandDeployments` ready, then phase `Disabled` or `DisableIncomplete` within
  `waoparams.OperandDisabledTimeout` and every one of those Deployments `NotFound`.
- `workload-availability-operator-controller-manager` is untouched throughout; the spec never
  asserts on it beyond excluding it from the precondition check.
- Cleanup finishes: `spec.components` has all six operands disabled again, and the only
  Deployment left in the namespace is WAO's own manager.

## 8. Failure / known issues

None.

## 9. Cleanup

- `DeferCleanup` disables all six operands in a single patch, whether or not the spec failed
  part way through, so a failure between enable and disable does not leave an operand
  installed. Failures are logged with `GinkgoWriter.Printf` rather than asserted, so cleanup
  cannot mask the original failure.
- `AfterAll` removes nothing: `BeforeAll` only reads.
- **Not cleaned up**, because removing it needs the operand's own procedure rather than a WAO
  setting: anything reported in `status.components[].retainedResources`. After a passing run
  that is the `SelfNodeRemediationConfig` and the agent DaemonSet it owns, with an agent pod
  per node. They fail precondition 3 on the next run. Clear them with:

  ```bash
  oc get workloadavailabilityconfig cluster \
      -o jsonpath='{range .status.components[*]}{.name}{" "}{.phase}{" "}{.retainedResources}{"\n"}{end}'
  oc delete selfnoderemediationconfig --all -n openshift-workload-availability
  ```

  Deleting the config is enough and is safe with the operand disabled: the config carries no
  finalizer, so it does not need the stopped SNR manager to release it, and the DaemonSet is
  removed by garbage collection because the config owns it. Within a few seconds the operand
  returns to `Disabled` and the namespace holds only WAO's own manager again.

  `scripts/clear-remediation-state.sh` clears medik8s taints, labels, annotations and
  remediation CRs if a previous remediation left node state behind.

## 11. Running it standalone

```bash
ginkgo -v --label-filter="operator:wao" \
    --focus="enables each operand" ./tests/wao-operator/...
```

Watch the cluster while it runs:

```bash
watch -n 5 -d tools/watch/wao-watch.sh   # Linux, or macOS with `brew install watch`
tools/watch/wao-watch.sh --loop          # anywhere, no `watch` needed
```

`wao-watch.sh` shows four blocks: the per-operand `DESIRED`/`PHASE`/`ADMIT`/`RETAINED` rows of
the singleton, WAO's own `Available`/`Progressing`/`Degraded` conditions, the Deployments and
DaemonSets in the namespace with their ready counts, and the pods.

What must change: one operand at a time moves `Disabled` → `Progressing` → `Available` and back,
and its Deployment appears then disappears. What must not change:
`workload-availability-operator-controller-manager` stays `1/1` throughout — if WAO's own
manager restarts, the operand phases are reporting a WAO recovery rather than operand health.
An operand sitting in `Progressing` with its Deployments ready and `ADMIT=false` is waiting for
the service CA controller to inject a webhook CA bundle, not failing.

## 12. Implementation sketch

Implemented in
[`tests/wao-operator/tests/operand_lifecycle.go`](../../tests/wao-operator/tests/operand_lifecycle.go).

```go
It("RHWA-2040: enables each operand, waits for it to start, then disables it",
    reportxml.ID("2040"),
    Label(
        labels.OperatorWAO,
        labels.TierSmoke,
        labels.ComponentController,
        labels.DisruptionNonDestructive,
        labels.PlatformAny,
    ), func() {
        DeferCleanup(func() {
            By("DeferCleanup: disabling every operand")
            restoreAllOperandsDisabled()
        })

        for _, operand := range medik8sparams.WAOAllComponents {
            enableOperand(operand)
            disableOperand(operand)
        }
    })
```

The patching itself is in `tests/internal/helpers/wao.go`: `SetWAOComponents` takes a
`map[string]bool` and applies any combination of operands in one merge patch, with
`EnableWAOComponents` / `DisableWAOComponents` as the variadic wrappers this spec uses.
