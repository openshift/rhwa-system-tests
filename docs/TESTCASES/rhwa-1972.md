## 2. Summary

`SelfNodeRemediationConfig.spec.minPeersForRemediation` is rendered onto the agent
DaemonSet as `MIN_PEERS_FOR_REMEDIATION`, but before the RHWA-1872 fix the agent never read
that variable and used the Go zero value `0` instead. Two specs inject the *same* fault on
two different workers — the agent pod is cut off from the api-server and from every peer
agent — and differ only in the configured minimum:

| Spec | `minPeersForRemediation` | Agent branch | Node |
| ---- | ------------------------ | ------------ | ---- |
| reboot (positive control) | `0` | asks its peers, hears nothing, `UnHealthyBecauseNodeIsIsolated` | reboots |
| no reboot (the bug) | Ready worker count, always one more than the node can find | `len(peersToAsk) < MinPeersForRemediation`, `HealthyBecauseNoPeersWereFound` | stays up |

The pair is the assertion. A node that stays up is only evidence that the configured
minimum was honoured because the identical fault demonstrably reboots a node when the
minimum is `0`.

## 3. Scope

- **In scope**: the agent's effective `MinPeersForRemediation`, asserted behaviourally.
  That the controller renders `MIN_PEERS_FOR_REMEDIATION` from the SNRC onto the running
  agent pod, and that an agent which has lost both api-server access and every peer
  remediates its node when it needs no peer to agree, and leaves it alone when the
  configured minimum is out of reach.
- **Out of scope**:
  - The remediation path driven by a `SelfNodeRemediation` CR, and the strategies that
    evict workloads. Covered by `worker_remediation.go` and `master_remediation.go`. The
    reboot here is the agent's own isolation verdict; no CR is ever created.
  - The single-worker isolated-node case (`len(peersToAsk) == 0`). Both specs keep at least
    one peer in the list, and reach the isolated verdict through unanswered peer requests
    instead.
  - Control plane agents. The specs patch the one cluster-wide SNRC, so every agent picks
    the value up, but they inject the fault on and assert against workers only; control
    plane peer handling is `master_remediation.go`.
  - The remaining `ApiConnectivityCheckConfig` fields PR #363 also routed through
    `getApiConnectivityCheckConfigFromEnv` (`API_CHECK_INTERVAL`, `HOST_PORT`, …). Those were
    already read before the fix; `config_lifecycle.go` and `upgrade_lifecycle.go` cover
    SNRC-to-DaemonSet propagation generally.
  - The other SNRC field defaults and their CRD validation, covered by `crd_negative.go`.

## 5. Preconditions

1. The SNR operator is installed in `openshift-workload-availability` and
   `self-node-remediation-controller-manager` is Ready. `BeforeAll` pulls the deployment and
   asserts `IsReady` within `medik8sparams.DefaultTimeout`.
2. The cluster has at least `snrparams.MinWorkersForPeerCheck` (2) Ready worker nodes:
   one to reboot, one to leave alone, each of them a peer of the other. `BeforeAll` counts
   them with `helpers.CountReadyWorkerNodes` and `Skip`s with the observed count when there
   are fewer.
3. Two distinct worker nodes are selectable. `BeforeAll` calls `helpers.SelectWorkerNode`
   twice, excluding the first node from the second call; both avoid the SSH bastion node.
4. Every SNR agent DaemonSet pod is Running with ready containers, so the peer list the
   agent builds is complete before the value is changed. `BeforeAll` waits for
   `verifyDSPodsRunning` within `snrparams.DSPodRestartTimeout`.
5. No stale state needs deleting: the specs create no CR. They patch the single default
   `SelfNodeRemediationConfig`; `BeforeAll` reads the pre-existing `minPeersForRemediation`
   once and a container-scoped `DeferCleanup` restores it once, after both specs.

## 7. Pass criteria

- Two specs with `reportxml.ID("1972")` run and pass.
- In both, the `manager` container of the agent pod on the node under test carries
  `MIN_PEERS_FOR_REMEDIATION` equal to the patched `minPeersForRemediation`.
- With `minPeersForRemediation: 0`, the isolated node reboots: `status.nodeInfo.bootID`
  changes. This is the positive control — it fails on a fixed and a broken build alike, and
  its only job is to prove the fault injection reaches the agent's decision at all.
- With `minPeersForRemediation` at the Ready worker count — always at least 2, always one
  more than the most peers a single worker can see, always different from the CRD default of
  1 — the isolated node does *not* reboot and stays Ready. This is the assertion the bug
  fails.
- Cleanup finishes: the rebooted node is Ready again with its agent Running, no blackhole
  route remains in either agent pod, and `minPeersForRemediation` is back to the value read
  in step 6 with every agent pod Running and ready within `snrparams.DSPodRestartTimeout`.

## 8. Failure / known issues

| Issue | Effect | Gate |
| ----- | ------ | ---- |
| The agent image ships no `ip`. | The exec that injects the fault fails with `sh: ip: command not found` and exit 127, the agent never loses api-server access, and without the probe both specs would run their full isolation window and then fail on assertions about a fault that was never applied. `iproute` was added to the runtime image in self-node-remediation [`df364797`](https://github.com/medik8s/self-node-remediation/commit/df364797) (2026-05-21, in `medik8s-5.8`) precisely so e2e tests can simulate this disconnection; builds from before it, and downstream builds that did not pick it up, lack it. | Not gated, but detected early: `BeforeAll` probes for a working iproute2 command and the container **skips** with the list of commands it tried, before any SNRC patch rolls the DaemonSet. The `nsenter` fallback covers images that merely lack the binary while still having `util-linux`. |
| [RHWA-1942](https://redhat.atlassian.net/browse/RHWA-1942) — rolling the agent DaemonSet drives control plane nodes into watchdog self-remediation. | These specs patch the default SNRC up to three times (one per spec, plus the restore), and every patch rolls every agent pod cluster-wide. On current builds that has rebooted up to 2 of 3 control plane nodes per rollout, 79-169s after it, on two unrelated clusters. The first spec also sets `minPeersForRemediation: 0` **cluster-wide**, which removes the peer-confirmation guard for every agent, control plane ones included, for as long as it is set. | Not gated. It is why both specs carry `DisruptionDestructive` and must not run in a non-destructive lane. If a control plane node reboots here, read it as RHWA-1942 and not as a `minPeersForRemediation` result: these specs assert on two named workers only, and nothing they do targets a control plane node. |

The specs are not gated. RHWA-1872 is fixed in SNR 5.8.0 by self-node-remediation PR #363,
so they pass on any build from that PR onwards.

On a pre-fix build the second spec fails at step 16, and it fails by **rebooting a second
worker node**: the agent's effective `MinPeersForRemediation` is `0`, so
`len(peersToAsk) < 0` is never true, it asks peers it can no longer reach, and reaches the
same `UnHealthyBecauseNodeIsIsolated` verdict as the first spec. That is the intended
regression signal. Both nodes are waited back to Ready, but a run against a pre-fix build
reboots two workers rather than one.

Why the earlier log-based assertion was replaced: on a ≥ 2 worker cluster with only the
api-server blackholed, a fixed and a pre-fix agent both end at "no reboot" — the fixed one
through `HealthyBecauseNoPeersWereFound`, the pre-fix one because a reachable peer tells it
no `SelfNodeRemediation` CR exists. Nothing observable separated them except the log line.
Blackholing the peers as well removes that reachable peer, which is what makes the
difference behavioural.

## 9. Cleanup

- Spec 1's `DeferCleanup` best-effort removes any leftover blackhole route — normally a
  no-op, since the pod died with the node — then waits for the rebooted node to be Ready
  within `snrparams.NodeReadyTimeout` and for every agent pod to be Running again, so the
  second spec starts against a whole cluster.
- Spec 2's `DeferCleanup` removes any blackhole route left in its agent pod. It tolerates a
  vanished pod, logs failures with `GinkgoWriter.Printf` instead of failing, and — if a
  route somehow survives — deletes the agent pod so the DaemonSet recreates it with a clean
  network namespace. In the normal path the injecting command has already deleted the routes.
- A container-scoped `DeferCleanup` registered in `BeforeAll` runs last and restores
  `spec.minPeersForRemediation` to the value read in step 6, removing the field when it was
  unset so the CRD default of 1 applies. It waits for the agent pods to be replaced when the
  restore changes the value, and only for them to be Running when it does not — so a run
  that failed before patching anything does not block for `snrparams.DSPodRestartTimeout`.
- `AfterAll` removes nothing: `BeforeAll` creates no resource.
- Recovery runs even when a spec fails mid-way, because every cleanup is a `DeferCleanup`
  closure registered before the step that can fail. No node is ever cordoned, no kubelet is
  stopped and no host route is changed; the only node-level effect is the expected reboot.

### Watching the cluster while it runs

These specs reboot a node on purpose, so it helps to watch the cluster rather than read
the reboot back out of the Ginkgo log afterwards.
[`tools/watch/snr-watch.sh`](../../tools/watch/snr-watch.sh) prints one snapshot of
everything an SNR remediation touches:

```bash
watch -n 5 -d tools/watch/snr-watch.sh   # Linux, or macOS with `brew install watch`
tools/watch/snr-watch.sh --loop          # anywhere, no `watch` needed
```

`-d` is what makes `watch` useful: it highlights whatever changed since the previous tick,
so a boot ID flipping or a taint appearing stands out instead of having to be spotted by
eye. macOS ships no `watch`, so `--loop` does the same in-script, marking changed lines
with a leading `*`.

| Block | Shows | Why it matters here |
| ----- | ----- | ------------------- |
| `nodes` | name, `Ready`, cordon, full `status.nodeInfo.bootID`, and taint keys, values and effects | The boot ID is what both specs assert on. Record the two nodes under test before the run: one must change, the other must not |
| `remediation CRs` | `SelfNodeRemediation` and `NodeHealthCheck` across all namespaces | Must stay empty. These specs create none -- the reboot is the agent's own isolation verdict, so a CR appearing means something else is acting on the cluster |
| `snrc` | live `spec.minPeersForRemediation` | Tracks the run: `0` for the first spec, the Ready worker count for the second, back to its original value at cleanup |
| `agent pods` | name, ready, status, age, node | Pod ages make a DaemonSet rollout -- or a single agent restarting unexpectedly -- obvious at a glance |

The reboot shows up in three stages, in this order, and the last one is the slowest:

1. `Ready` becomes **`Unknown`**, not `False`, roughly 40s after the kubelet stops
   heartbeating. `Unknown` is the node-lifecycle controller marking a stale status, which
   is right for a node that vanished rather than one reporting itself unhealthy.
2. The taint manager adds `unreachable` and `not-ready`. Both appear twice, once
   `NoSchedule` and once `NoExecute`; the taint column includes the value and effect when
   present.
3. `bootID` changes. This comes **last**: `status.nodeInfo.bootID` only updates when the
   kubelet re-registers, so the new value appears when the node comes *back*, not when it
   goes down.

A cordon should never appear. Nothing in these specs drains or cordons a node.

Each tick costs one `oc get nodes -o json` plus three small reads. That is negligible, but
raise `-n` if you would rather not add API traffic during a spec that is itself about
api-server connectivity.

## 12. Implementation sketch

Implemented in
[`tests/snr-operator/tests/min_peers_for_remediation.go`](../../tests/snr-operator/tests/min_peers_for_remediation.go).

The fault is injected from inside the agent pod's own network namespace — the agent
container is privileged, runs as uid 0 and ships `iproute` for exactly this purpose
(self-node-remediation `df364797`) — so the node, its kubelet and every other pod on it
keep full api-server access. Peers are blackholed at their *agent pod IP*: that is how the
agent addresses them, since `peers.go` builds the peer list with `mapNodesToPrimaryPodIPs`,
so no node address is involved.

`BeforeAll` probes for a usable `ip` before patching anything, trying `ip`, `/usr/sbin/ip`,
`/sbin/ip` and finally `nsenter -m/proc/1/ns/mnt -- ip`, which borrows the host's binary
through the host mount namespace while staying in the pod's *network* namespace. If none
works the container skips, naming the commands it tried.

```go
It("Verify an isolated agent reboots its node when minPeersForRemediation is zero", ...,
    func() {
        agent := prepareIsolatedAgent(ctx, rebootNodeName, snrparams.MinPeersRemediateAlone)

        isolateAgent(agent, snrparams.IsolationRebootHoldDuration)

        Expect(helpers.WaitForNodeReboot(ctx, APIClient, rebootNodeName, agent.bootID,
            snrparams.DefaultPollInterval, snrparams.NodeReadyTimeout,
            GinkgoWriter.Printf)).To(Succeed(), ...)
    })

It("Verify an isolated agent leaves its node alone when minPeersForRemediation is out of reach", ...,
    func() {
        // The Ready worker count: one more than any peer count a single
        // worker can observe.
        agent := prepareIsolatedAgent(ctx, healthyNodeName, int64(readyWorkerCount))

        // Gated: a node that was never cut off trivially does not reboot.
        Expect(isolateAgent(agent, snrparams.IsolationHoldDuration)).To(Succeed(), ...)

        Consistently(func() error {
            return verifyNodeNotRebooted(ctx, healthyNodeName, agent.bootID)
        }, snrparams.RebootSettleWindow, snrparams.DefaultPollInterval).Should(Succeed(), ...)
    })
```
