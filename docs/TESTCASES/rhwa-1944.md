This is the Block-mode counterpart of the Filesystem total storage I/O loss test
(`tests/sbr-operator/tests/storage_loss_watchdog.go`, OCP-88880). It carries its
own `reportxml.ID("1944")` rather than sharing the Filesystem test's ID, so the
two runs report as distinct results — the same pattern the block node hang test
(RHWA-1931) and the block split-brain test (RHWA-1934) follow.

## 2. Summary

One worker node running SBR in Block volume mode on Ceph RBD loses its storage
entirely: Ceph traffic is blocked in both directions, so the node can neither
write its heartbeat nor read the fence message its peers write into its own fence
slot. The only path left to a reboot is the watchdog — the node's own agent sees
a `StorageBasedRemediation` CR for itself and stops petting — and the test proves
that the node is rebooted that way, that fencing is proven from storage, and that
the node recovers.

## 3. Scope

- **In scope**: the watchdog self-reboot path when a Block-mode node loses Ceph
  storage completely — storage-based detection (`SBRStorageUnhealthy=True`,
  reason `HeartbeatTimeout`), NHC creating the CR, the peer-side fencing proof
  (`FencingSucceeded=True` / `Succeeded=True`) and `out-of-service` taint, the
  victim's reboot (boot-id change), its return to Ready with a Ready agent pod,
  no second fence, and cleanup back to schedulable with the taint removed.
- **Out of scope**:
  - The same scenario on RWX **Filesystem** storage
    (`storage_loss_watchdog.go`, OCP-88880).
  - Proving *which* mechanism rebooted the node from the node's own side: the
    agent is gone with the reboot, so the watchdog is inferred from the node
    being cut off from storage and still rebooting, not read from a counter.
  - Witness-side split-brain assertions — that fencing hits only the isolated
    node (`block_storage_split_brain.go`, RHWA-1934).
  - The single-victim remediation path with storage intact
    (`block_storage_node_hang.go`, RHWA-1931).
  - Recovery from a *transient* Ceph RBD partition without fencing
    (`block_storage_transient_partition.go`, RHWA-1924).
  - The write-only storage loss variant (`storage_loss_write_only.go`, OCP-89200).
  - Block device on-disk layout correctness (`block_storage_inspection.go`,
    RHWA-1926) and heartbeat stability under load
    (`block_storage_heartbeat_load.go`, RHWA-1925).

Environment variables:

```bash
export KUBECONFIG=/absolute/path/to/kubeconfig
export ECO_TEST_FEATURES=sbr-operator
export ECO_TEST_LABELS='operator:sbr && component:remediation'
# Optional:
export SBR_RBD_STORAGE_CLASS=<ceph-rbd-storageclass>          # overrides RBD auto-discovery
export SBR_INJECTOR_IMAGE=<ubi9 image with nsenter+iptables>  # required in disconnected clusters
```

- `SBR_RBD_STORAGE_CLASS` — the Ceph RBD StorageClass. When unset, a StorageClass
  whose provisioner contains `rbd.csi.ceph.com` is auto-discovered; the test
  **skips** when none exists.
- `SBR_INJECTOR_IMAGE` — image for the privileged injector pod; must ship
  `nsenter` and `iptables`. Defaults to `registry.access.redhat.com/ubi9/ubi:latest`;
  must be mirrored and set in disconnected clusters.

## 5. Preconditions

1. The `NodeHealthCheck` CRD is installed (otherwise the test skips).
2. At least one schedulable worker node hosts no SBR controller pod; that one is
   the victim, so the reboot does not take the operator down mid-test. Otherwise
   the test skips.
3. iptables is usable in the victim node's host namespaces (probe pod); otherwise
   the test skips.
4. No pre-existing `NodeHealthCheck` from a prior run of this test
   (`nhc-sbr-block-storage-loss`) — it is deleted and waited out in `BeforeAll`.
5. No other `NodeHealthCheck` remediates through the SBR template
   (`requireNoSBRNodeHealthCheck`), which would fence a node independently.
6. Self Node Remediation is not running (SNR and SBR cannot share the watchdog).
7. A Ceph RBD `volumeMode: Block` StorageClass exists.
8. The Block device-init Job for the test SBRC completes successfully and the
   agent DaemonSet becomes ready. Agent readiness is gated on preflight, which is
   what arms the watchdog this test depends on.
9. The SBRC reports `status.storageValidation.concurrentWriteable=true`, the gate
   the reconciler reads before it will fence anything.

## 6. Test steps

| #  | Step (`By` text)                                                                                     | Expected result                                                                 |
| -- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1  | Recording the victim node's boot-id before the storage loss                                          | Pre-loss victim boot-id read                                                    |
| 2  | Asserting SBRStorageUnhealthy is not True on the victim node                                         | Victim's `SBRStorageUnhealthy` is absent, False or Unknown (not True)           |
| 3  | Starting a privileged injector pod that blocks Ceph traffic in both directions on the victim node    | REJECT rules for ports 3300, 6789, 6800–7300 applied on both the OUTPUT and INPUT chains of the victim only, with no time limit |
| 4  | Waiting for SBRStorageUnhealthy=True (reason HeartbeatTimeout) on the victim node                    | A peer sets `SBRStorageUnhealthy=True` with reason `HeartbeatTimeout`            |
| 5  | Waiting for NHC to create a StorageBasedRemediation CR for the victim node                           | `StorageBasedRemediation/<victim>` exists — the CR the victim's own agent looks for before it stops petting the watchdog |
| 6  | Waiting for FencingSucceeded=True and Succeeded=True on the victim's StorageBasedRemediation CR       | Both conditions reach True (CR looked up by node name on every poll)             |
| 7  | Asserting the victim node carries the out-of-service taint                                            | Victim has `node.kubernetes.io/out-of-service`                                   |
| 8  | Waiting for the victim node's boot-id to change (the watchdog rebooted it)                            | Victim boot-id differs from the pre-loss boot-id                                |
| 9  | Waiting for the victim node to come back Ready                                                        | Victim reports `Ready=True`                                                      |
| 10 | Waiting for the victim node's agent pod to be Ready again                                             | This SBRC's agent pod on the victim reaches `PodReady=True`                      |
| 11 | Consistently asserting that the victim is not fenced again (stable boot-id and Ready)                 | For 90s the victim keeps its new boot-id and stays `Ready=True`                  |
| 12 | Waiting for NHC to delete the StorageBasedRemediation CR                                              | `StorageBasedRemediation/<victim>` is gone (`IsNotFound`)                        |
| 13 | Asserting the victim node is schedulable again and the out-of-service taint is gone                   | Victim is schedulable and carries no `out-of-service` taint                      |

Two deliberate deviations from the planned step order, both recorded here rather
than in the spec's scope:

- The planned order waits for the boot-id change **before** `FencingSucceeded`.
  That is racy: death is proven from the victim's heartbeat slot going stale,
  which it already has, so the proof lands long before kubelet reports a new
  boot-id — and once the victim is back its iptables rules are gone with the
  reboot, it heartbeats again, NHC deletes the CR and the reconciler removes the
  taint. A check that waits the reboot out first can find neither. Steps 6 and 7
  therefore precede step 8.
- Step 7 (the `out-of-service` taint) is not in the plan. Without it the plan's
  final "the taint is gone" assertion proves nothing, and both sibling block
  tests assert it at the same point.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1944")` runs and passes.
- After both directions of Ceph traffic are blocked, a peer reports the victim
  `SBRStorageUnhealthy=True` (reason `HeartbeatTimeout`) within
  `StorageInjectionTimeout`.
- NHC creates a `StorageBasedRemediation` named after the victim within
  `NHCSBRCRCreationTimeout`.
- That CR reaches `FencingSucceeded=True` **and** `Succeeded=True` within
  `FencingProvenTimeout`, and the victim carries the
  `node.kubernetes.io/out-of-service` taint.
- The victim's boot-id changes within `NodeRebootTimeout` — with its storage gone
  it cannot read its fence slot, so the reboot came from the watchdog — and the
  node returns `Ready` and its agent pod reaches `PodReady=True`.
- For `BlockNoFencingCheckDuration` (90s) the victim keeps that boot-id and stays
  Ready: it is not fenced a second time.
- NHC deletes the CR within `SBRCRCleanupTimeout`, and the victim becomes
  schedulable with the `out-of-service` taint removed.
- Cleanup finishes: the NHC, SBRC and injector pod are gone, no
  `StorageBasedRemediation` remains, the victim is uncordoned, and any leftover
  Ceph REJECT rule is flushed.

## 8. Failure / known issues

None.

Three design notes, none a known bug:

- RBD I/O usually **hangs** on connection loss rather than erroring. If the
  boot-id wait (step 8) times out, the likely cause is an agent stuck in a
  blocked write with the watchdog never firing — a product behaviour, not a test
  defect, and worth reporting as such.
- If NHC deletes the CR when `SBRStorageUnhealthy` cycles to `Unknown` (reason
  `GivingAgentChance`), the victim resumes petting the watchdog until the CR is
  recreated. `NodeRebootTimeout` (20 min) covers more than one full cycle.
- `FencingInProgress` is deliberately never asserted: the 60s fencing window and
  the 60s heartbeat-staleness threshold are both hardcoded, so the condition
  flaps and a `FencingFailed` event is a normal retry rather than a failure.

## 9. Cleanup

- `DeferCleanup` removes the injector pod and flushes any Ceph REJECT rule left
  on the victim node (`flushCephRBDRules` deletes both chains, so it removes
  exactly what the bidirectional injection inserted).
- `AfterAll` removes the `NodeHealthCheck`, deletes the injector pod, flushes
  leftover Ceph rules on the victim, force-removes any `StorageBasedRemediation`
  for the victim, uncordons it if still cordoned, and deletes the SBRC (waiting
  for it to be gone). All tolerate `IsNotFound`.
- Recovery (iptables flush, uncordon) runs even when the spec failed mid-way.
- `BeforeAll` pre-cleans the test's own stale NHC and SBRC from a prior run and
  waits for them to be fully gone before recreating.
