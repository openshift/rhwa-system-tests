## 2. Summary

These tests check storage reporting, NHC remediation, autonomous reboots, workload evacuation, and complete worker recovery.
They use host boot IDs, public Kubernetes resources, and confirmed host faults. They do not parse product logs or journals.

## 3. Scope

The suite contains 22 cases.
Cases 04, 21, and 22 enable the optional boot unit. All other cases explicitly disable it.
Positive remediation requests must originate from NHC. Only the unauthorized-request case creates remediation CRs from the runner.
Ordinary workload Pods tolerate not-ready and unreachable NoExecute taints indefinitely. They do not tolerate OOS.
Their original UIDs must disappear after OOS. Workload recovery is outside scope.
The finalizer-held Pods in cases 15A and 15B deliberately remain to test cleanup and restriction ownership.

The boot-unit cases check cordon publication and service order separately. They cannot establish the exact order of publication and kubelet startup.
Case 15B checks administrator restrictions with the boot unit disabled. The boot-unit cases use worker Nodes.

Version upgrades, power loss, general kernel freeze, unknown journal history, VM recovery, and volume-detach evidence remain outside scope.
A changed boot ID does not identify the reboot mechanism or count unseen boots during an SSH blackout.
Case 17F configures three-minute recovery. Other autonomous cases configure one minute. Defaulting and explicit five-minute recovery remain outside scope.

| Topology | All detected workers selected by one test-owned label. |
| Platform | Any platform with the required existing host access. |
| Storage | One dynamically provisioned Ceph RBD StorageClass with raw Block support. Cases 04, 07, 18, and 20 require RWX Block for concurrent target and read-only watcher mounts. |

| Host commands | Existing `ssh`, `sh`, `sudo`, `systemctl`, `iptables`, and `ip`. Journal cases need `chattr` and `lsattr`. |

Let `N` be the number of Nodes with the `node-role.kubernetes.io/worker` label at case setup.
Fail setup if `N < 2` or any detected worker fails the platform and readiness requirements.
Sort workers by Node name. Index `0` is target A. Indices `1` through `N-1` are its peers.
Use every detected worker for configuration, observations, and cleanup. Do not select a fixed subset.
A two-worker cluster has one peer. Group partitions preserve traffic among peers when multiple peers exist.

Do not install packages. Do not use an injector image, helper image, `oc debug`, or a new external service.
Do not open or feed a watchdog. Do not add a separate watchdog qualification procedure.

### NHC policies

Case 03 selects every worker and sets integer `minHealthy: N-1`.
Cases that must request remediation while peers are unhealthy use a target-only selector with `minHealthy: 0`.
All selected workers remain part of SBR configuration, observation, and recovery checks.
NHC observes only `SBRStorageUnhealthy=True`, with an unhealthy duration of 30s and `healthyDelay: 1m`, except case 19.
Case 19 keeps target-only NHC active with a one-hour unhealthy duration. Both unauthorized-request observations must finish before eligibility.
Never add `Ready=False` or `Ready=Unknown` to the policy.

Pause NHC during autonomous-only phases. Case 19 uses active NHC to isolate the request provenance check. Read the stored pause state after each change.
Pausing NHC also pauses its healthy-node deletion path. Delete tracked CRs normally when a phased case requires runner-driven deletion.
Resume NHC only when the next requested phase starts. Never fabricate an owner reference to obtain a positive request.

Case 03 records the target CR before disrupting peers. Restore peer storage before target storage to prevent unintended peer requests during recovery.
Case 10 uses confirmed peer storage timeouts before it makes the target eligible for NHC remediation.
Case 17B keeps storage unavailable across request A, an autonomous reboot, request B, and the final no-reboot interval.

## 5. Preconditions

1. Require at least two workers. Record every worker's Node UID, host/API boot IDs, cordon, and complete taint list.
2. Require initial host and API boot IDs to match. Prepare existing SSH and management routes before disruption.
3. Register cleanup before the first mutation. Reject conflicting remediation policies or configurations.
4. Start Node, CR, Pod, and host observations before the case trigger.
5. Require complete initial lists and watches. Preserve timestamps, UIDs, watch gaps, and replay evidence.
6. Create the test configuration and NHC fixtures. Check that the API retains the submitted settings.
7. Require all agents and reporters to become Ready. Require healthy storage on all workers.
8. Check the existing watchdog device and configured timeout after agent readiness. Do not open or feed the watchdog.
9. For cases that evacuate a workload, require the original Pod to be Running and Ready before disruption.
10. Observe the healthy baseline before the first fault. Autonomous cases also require known history and the configured recovery interval.

Missing proposed fields or behavior causes FAIL. Missing native fault facilities can block a case before activation.
A watch gap cannot establish a negative result. A replacement Node UID cannot satisfy an assertion for the original Node.
Do not reset public history, clear journals, remove product finalizers, or repair state to make a case pass.

| Fault | Required effect and confirmation |
|---|---|
| API loss | Reject all discovered API paths for the affected host, agent, and reporter. Preserve runner API access and SSH. |
| Storage loss | Reject discovered Ceph monitor and OSD traffic. Confirm owned rules and matching traffic. Preserve API access unless explicitly blocked. |
| Storage timeout | Drop the same storage traffic. Confirm matching traffic. Do not infer a specific kernel I/O state. |
| Single-worker isolation | Block API and peer traffic. Preserve storage and management traffic. |
| Group partition | Block both directions between the target and its peers. Preserve API, storage, and management traffic. |
| Kubelet stop | Stop kubelet through SSH and confirm inactive state. Preserve CRI-O and the agent. |
| Journal writes | Make the existing journal directory immutable. Confirm failed temporary file creation without reading or changing the journal. |
| Watcher reads | Fail only the watcher host's mapping of the target probe. Confirm failed direct reads without disrupting any writer. |

Persistent network faults must remain active across reboot. Confirm service ordering before activation and rules after reconnection.
In enabled cases, the fault services reapply the rules before the boot unit starts. The API rules include the kubelet API endpoint.
Check the agent-installed unit and its ordering before disruption. Use host monotonic service timestamps for timing evidence.
A changed boot ID alone does not prove that kubelet started. Missing host timing evidence cannot produce PASS.
Enabled cases require systemd main-process start and exit timestamps for the service in the current boot.
Case 04 allows 5s timing tolerance and 30s for kubelet startup after the boot unit exits.
A fault that disappears during reboot cannot establish continued-outage behavior.

For cases 04 and 18, block target API access before storage. Require no earlier request or restriction.
Keep NHC active so external reporting can create the target CR while the target cannot report through the API.
For autonomous-only phases, pause NHC and confirm storage failure before blocking the API.

Case 17E keeps storage available across an API interruption. A retained False condition alone does not establish individual probe completion.
Its final reboot checks the externally observable rearm result.
Case 17F confirms unhealthy storage between two sub-threshold recovery intervals. Their combined healthy time must exceed the recovery period.
Both cases preserve target agent identity during recovery intervals. Missed timing bounds cannot produce PASS.

### RHWA-2092-02 API loss with healthy storage - No worker reboots

One worker and then all workers lose API access. Every worker retains its boot ID and has no remediation CR or restriction change.

|---|---|---|

## 7. Pass criteria

Every required step and cleanup assertion must pass. A successful SSH dispatch, elapsed timer, or current GET cannot replace required historical evidence.

### Remediation and evacuation

- Require a genuine NHC-owned CR with stable CR and Node identities for every positive requested path.
- Check policy success when OOS is confirmed. Check all five success conditions and `cleanup.outOfServiceApplied` independently of cleanup completion.
- Check the saved policy, grace deadline, and policy reason. Timeout success must use `RebootGraceExpired`.
- Check requested and autonomous boot changes through actual host boot IDs. Require peer boot IDs to remain unchanged.
- Match requested reboot evidence to the original CR, Node, and before/after host boot IDs. Reject observed pre-request boot changes.
- Case 15A checks the original request boot ID before CR deletion. It checks the target boot change after deletion.
- Require each ordinary workload's original Pod UID to disappear within 300s after observed OOS, including OnTimeout cases.
- Do not require replacement workload readiness. Held-Pod cases deliberately check a different result.
- Keep cleanup timestamps fixed. CR deletion can finish before workload observation finishes.

## 8. Failure / known issues

These draft cases require an SBR build that supports the proposed BlockPerNode behavior.
Offline checks do not establish live behavior.
Missing unhealthy reporting, policy evidence, OOS, required evacuation, or recovery causes FAIL.
Missing history or a missed timing bound cannot produce PASS. Report the missing evidence explicitly.
Case 07 needs a crash long enough for unhealthy reporting and NHC request creation. A reboot alone cannot pass.
Case 20 requires kernel RBD, existing debugfs, CONFIG_FAIL_MAKE_REQUEST, and a separate watcher-host mapping of the target probe.
It requires native `nsenter`, `timeout`, `dd`, `stat`, and block-device metadata. It installs no packages or modules.
The fixture checks `/sys/dev/block/<major>:<minor>/make-it-fail` and `/sys/kernel/debug/fail_make_request` before activation.
It refuses active fault injection or another selected block device. It restores the saved controls during normal and deferred cleanup.
Direct I/O must fail with EIO on the watcher mapping while the writer completes writes and retains read access.
See the [Linux fault-injection interface](https://docs.kernel.org/6.12/fault-injection/fault-injection.html).
The proposal does not specify the watcher observation JSON schema. Case 20 checks health preservation rather than an invented `Unknown` field.
Do not substitute a Pod firewall or host-wide Ceph fault for an isolated block-device read fault.

## 9. Cleanup

Register every mutation before activation. Restore faults even if an earlier assertion fails.

1. Remove owned network and watcher device faults. Restore saved fault-injection settings and persistent services.
2. Restore original journal directory flags and confirm temporary file creation. Preserve journal contents.
3. Restore saved SysRq settings. Restart kubelet if the case stopped it.
4. Restore storage and API access. Require healthy storage and original Node UIDs.
5. Finish or normally delete tracked CRs. Require restriction release without removing SBR finalizers manually.
6. Preserve administrator-owned cordons and taints. Remove only administrator fixtures introduced by the test after checking preservation.
7. Require complete worker recovery, including boot-cordon release, while SBR remains installed.
8. Remove only test-owned workload finalizers. Delete test Pods and namespaces normally.
9. Delete NHC, the template, and the configuration normally. Require owned operands and storage fixtures to disappear. In enabled cases, check that the agent-managed boot unit is removed or disabled.
10. Restore all worker labels after configuration shutdown. Stop observers after final recovery checks.

Case 03 restores all peers before the target. Cases 04, 06, 07, and 18 allow NHC to delete their CR after recovery.
Case 17B pauses NHC before explicitly deleting each completed request. It preserves storage failure between request cycles.
Case 15A retains its Pod finalizer through CR deletion. Case 15B retains its Pod and administrator fixtures through their required checks.
Case 20 restores the native device fault before normal fixture cleanup, including after an assertion failure.

Collect cleanup errors. Preserve fixtures if unresolved request ownership or restriction release makes further deletion unsafe.
A failed recovery blocks later disruptive cases. Never erase autonomous history to continue the suite.


The display shows full Node boot IDs, UIDs, storage and rejoin conditions, cordons, ownership annotations, taints, and CR conditions.
It also shows cleanup times and namespace Pods.
A missing storage condition appears as `<unset>`. A failed API read appears as a failed read, not healthy state.
Record baseline boot IDs before the run. Required no-reboot intervals must preserve those IDs.
Agent replacement changes the Pod UID. An accepted requested reboot changes the target boot ID.
The display cannot replace the host sampler or continuous API recorder. API boot IDs can remain stale while kubelet cannot report.
