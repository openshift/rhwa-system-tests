This is the Block-mode counterpart of the Filesystem SBRC lifecycle test
(`tests/sbr-operator/tests/sbrc_lifecycle.go`, OCP-88734). It carries its own
`reportxml.ID("1960")` rather than sharing that ID, so the two runs report as
distinct results — the same pattern the block node hang test (RHWA-1931) and the
block split-brain test (RHWA-1934) follow.

## 2. Summary

Creates, patches, replaces and deletes a `StorageBasedRemediationConfig` with
`sharedStorageVolumeMode: Block` on a Ceph RBD StorageClass, and asserts the
steps the operator only takes in Block mode: the RWX raw-block PVC, the device-init
Job that must finish before any agent starts, the `volumeDevices` attachment at
`/sbr-block`, the watchdog moved to `/host-dev`, the immutable volume mode, and the
absence of the Filesystem-only node map cleanup Job on delete.

## 3. Scope

- **In scope**: the Block-mode SBRC lifecycle on Ceph RBD — rejection of a
  Block-mode config with no `sharedStorageClass`; the shared-storage PVC being
  `ReadWriteMany` with `volumeMode: Block`; the device-init Job succeeding and
  gating the agent DaemonSet; the DaemonSet attaching the device through
  `volumeDevices` (never `volumeMounts`); the agent args
  `--sbr-device=/sbr-block` and `--sbr-file-locking=false`; the watchdog's parent
  directory mounted at `/host-dev` with the host `/dev` not mounted; the
  immutability of `sharedStorageVolumeMode`; a `sbrTimeoutSeconds` patch rolling
  the DaemonSet out on every node; deletion removing the DaemonSet and the PVC
  without running a node map cleanup Job; and a second SBRC getting a fresh PVC
  and a fresh init Job.
- **Out of scope**:
  - The same lifecycle on RWX **Filesystem** storage (`sbrc_lifecycle.go`,
    OCP-88734), including the node map cleanup Job that mode *does* run.
  - The on-disk layout and content of the block device
    (`block_storage_inspection.go`, RHWA-1926) and concurrent agent writes to it
    (`block_storage_multi_writer.go`, RHWA-1915).
  - Any remediation or fencing behaviour — no node is made unhealthy, no
    `StorageBasedRemediation` CR is created. Those are covered by
    `block_storage_node_hang.go` (RHWA-1931), `block_storage_split_brain.go`
    (RHWA-1934) and `block_storage_total_loss.go` (RHWA-1944).
  - Two SBRCs running **at the same time**. Every agent holds `/dev/watchdog`
    exclusively, so a second DaemonSet on the same nodes crash-loops on EBUSY;
    A is fully deleted before B is created.
  - Fencing state persistence across reboot (`block_storage_rbd.go`, RHWA-1916).

## 5. Preconditions

1. Self Node Remediation is not running (`failIfSNRRunning`) — SNR and SBR cannot
   share the watchdog, and the spec fails with scale-down instructions rather than
   producing crash-looping agents.
2. The installed SBR CRD ships `spec.sharedStorageVolumeMode`
   (`requireSBRCBlockVolumeModeSupport`). Below `FirstSBRCsvWithBlockVolumeMode`
   (`5.8.0`) the spec skips; at or above it, a missing field fails the suite, and an
   unknown CSV version fails rather than skipping a capable operator.
3. A Ceph RBD StorageClass exists, or `SBR_RBD_STORAGE_CLASS` names one; otherwise
   the spec skips.
4. No SBRC named `test-sbrc-block-lifecycle-a`, `test-sbrc-block-lifecycle-b` or
   `test-sbrc-block-no-storage-class` is left over from a prior run — each is
   deleted and waited out, and its agent DaemonSet waited out for GC, in
   `BeforeAll`. The storage-class-less name is pre-cleaned too: left behind, its
   create in step 1 would come back `AlreadyExists` and validate nothing.

## 6. Test steps

| #   | Step (`By` text)                                                                                              | Expected result                                                                                           |
| --- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 1   | Step 1: Asserting a Block-mode SBRC without sharedStorageClass never gets agents                                 | With a validating webhook registered: the create is denied with `Forbidden`/`Invalid` naming `sharedStorageClass`. Without one: the create succeeds, the controller emits a `ValidationError` Warning, and no agent DaemonSet appears for 30s |
| 2   | Step 2: Creating Block-mode SBRC `test-sbrc-block-lifecycle-a` on Ceph RBD                                       | SBRC A is created with `sharedStorageVolumeMode: Block` and the RBD StorageClass                             |
| 3   | Step 3: Asserting the shared storage PVC is ReadWriteMany with volumeMode Block                                  | A PVC owned by SBRC A exists, has `ReadWriteMany` in its access modes, and `volumeMode: Block`               |
| 4   | Step 4: Waiting for the Block device-init Job to succeed                                                         | A Job owned by SBRC A reaches `Succeeded`; its completion time is read before TTL collection                 |
| 5   | Step 5: Waiting for the agent DaemonSet to be ready                                                              | `sbr-agent-test-sbrc-block-lifecycle-a` has all scheduled pods Ready                                         |
| 6   | Step 6: Asserting the agent DaemonSet was created only after the init Job succeeded                              | The DaemonSet's `creationTimestamp` is not earlier than the init Job's completion time                        |
| 7   | Step 7: Asserting the shared storage is attached as a raw device, not mounted                                    | The agent container has a `volumeDevices` entry at `/sbr-block` backed by the PVC, and no `volumeMounts` entry for that volume |
| 8   | Step 8: Asserting the agent args select the raw device with file locking disabled                                | Agent args contain `--sbr-device=/sbr-block` and `--sbr-file-locking=false`                                   |
| 9   | Step 9: Asserting the watchdog was moved to the side mount instead of /dev                                       | The watchdog's parent directory is mounted at `/host-dev`, the host `/dev` is not mounted at `/dev`, and the agent's watchdog path points under `/host-dev` |
| 10  | Step 10: Asserting sharedStorageVolumeMode cannot be changed after creation                                      | With a webhook registered: patching the mode to `Filesystem` is denied with `Forbidden`/`Invalid` naming the field, and a re-read shows the SBRC still in `Block`. Without one: skipped and logged — the rule has no reconcile-time counterpart |
| 11  | Step 11: Patching sbrTimeoutSeconds and waiting for the DaemonSet to roll out                                    | The patch is accepted; the DaemonSet's generation advances, is observed, and **every** scheduled pod is on the new revision, Ready, and none unavailable |
| 12–13 | Steps 12-13: Deleting SBRC `test-sbrc-block-lifecycle-a`, asserting no node map cleanup Job runs, and waiting for its DaemonSet and PVC to go | From the delete call until the SBRC is gone, no Job labelled `app.kubernetes.io/component=sbr-cleanup` with `sbrconfig=test-sbrc-block-lifecycle-a` is ever seen; the DaemonSet is GC'd and the PVC is gone |
| 14  | Step 14: Creating Block-mode SBRC `test-sbrc-block-lifecycle-b` on Ceph RBD                                      | SBRC B is created on the same RBD StorageClass                                                                |
| 15  | Step 15: Asserting the second SBRC gets its own PVC and its own init Job                                         | B's PVC has a different name and UID from A's; a Job owned by B succeeds                                     |
| 16  | Step 16: Waiting for the second SBRC's agents to be ready                                                        | `sbr-agent-test-sbrc-block-lifecycle-b` has all scheduled pods Ready                                         |

The spec runs `ContinueOnFailure`, so a failed assertion reports and the remaining
steps still run — a single failure does not hide the rest of the lifecycle.

## 7. Pass criteria

- Exactly one spec with `reportxml.ID("1960")` runs and passes.
- A Block-mode SBRC with no `sharedStorageClass` never gets an agent DaemonSet:
  refused at admission when a `ValidatingWebhookConfiguration` covers
  `storagebasedremediationconfigs` (`Forbidden` or `Invalid`, message naming
  `sharedStorageClass`), otherwise admitted and refused at reconcile with a
  `ValidationError` Warning event, with no DaemonSet for
  `NoNewDaemonSetCheckDuration` (30s).
- SBRC A's shared-storage PVC, matched by owner UID, appears within
  `SBRCReadyTimeout` (10m) with `ReadWriteMany` and `volumeMode: Block`.
- The device-init Job owned by SBRC A reaches `Succeeded` within `SBRCReadyTimeout`,
  and the agent DaemonSet's `creationTimestamp` is **not earlier** than that Job's
  completion time.
- The agent container attaches the PVC through `volumeDevices` at `/sbr-block` with
  no `volumeMounts` entry for it, carries `--sbr-device=/sbr-block` and
  `--sbr-file-locking=false`, mounts the watchdog's parent directory at `/host-dev`,
  does not mount the host `/dev` at `/dev`, and points `--watchdog-path` under
  `/host-dev`.
- When a webhook is registered, patching `sharedStorageVolumeMode` to `Filesystem`
  fails with `Forbidden`/`Invalid` naming the field, and a re-read still reports
  `Block`.
- After the `sbrTimeoutSeconds` patch, within `SBRCLifecyclePatchedTimeout` (3m) the
  DaemonSet's generation advances, `observedGeneration` catches up,
  `updatedNumberScheduled` and `numberReady` both equal `desiredNumberScheduled`
  (which is non-zero), and `numberUnavailable` is 0.
- Deleting SBRC A never produces a node map cleanup Job: polling at
  `CleanupJobWatchInterval` (1s) from the delete call until the SBRC is gone, at
  least one list succeeds and no matching Job is seen in any of them — a list error
  fails the step rather than counting as "none seen".
- SBRC A's DaemonSet is GC'd within `SBRCDaemonSetGCTimeout` (5m) and its PVC within
  `SBRCPVCGCTimeout` (5m).
- SBRC B gets a PVC with a different name and UID from A's and its own successful
  init Job, its agents become Ready, and its delete removes the SBRC, DaemonSet and
  PVC.
- Cleanup finishes: no `test-sbrc-block-lifecycle-a`, `test-sbrc-block-lifecycle-b`
  or `test-sbrc-block-no-storage-class` SBRC remains, and no agent DaemonSet or
  shared-storage PVC belonging to them is left in the operator namespace.

## 8. Failure / known issues

None.

Three design notes, none of them a known bug:

- **Step 1 and step 10 branch on webhook presence.** The `sharedStorageClass`
  rule is enforced by both the admission webhook and the controller, so step 1
  asserts whichever layer is present. `sharedStorageVolumeMode` immutability is
  webhook-only — with no webhook registered there is nothing to assert, and
  landing the patch anyway would leave steps 11–13 running against an SBRC that is
  no longer in Block mode, so step 10 skips and logs instead.
- **Step 6 uses "not earlier than" rather than strictly after.** Kubernetes
  timestamps are second-granular, so an operator that creates the DaemonSet in the
  same second the init Job completes is correct and must not fail.
- **Step 13 is folded into the delete.** The cleanup Job would live and die inside
  the finalizer drain, so the watch has to start with the delete call; looking
  afterwards would miss a Job that ran and was removed. It matches on the labels the
  operator sets (`app.kubernetes.io/component=sbr-cleanup`, `sbrconfig=<name>`)
  rather than on a guessed name, because the Job's owner is already gone by the time
  it could be observed.

## 9. Cleanup

- `DeferCleanup` removes the storage-class-less SBRC
  (`test-sbrc-block-no-storage-class`) — needed because on a cluster with no webhook
  it is admitted rather than rejected — and waits for it to be gone.
- `AfterAll` deletes `test-sbrc-block-lifecycle-a` and `test-sbrc-block-lifecycle-b`
  and waits for each to be gone. Both are no-ops on a clean run, since steps 12–13
  and 17 already deleted them.
- `BeforeAll` pre-cleans all three names from a prior run and waits for both the SBRC
  and its agent DaemonSet to be fully gone before the spec creates anything.
- All deletes tolerate `IsNotFound`; `deleteSBRCAndWait` logs delete failures with
  `GinkgoWriter.Printf` rather than failing the suite, while still asserting the
  object actually disappears so nothing leaks into the next suite.
- No node-level recovery is needed — the test cordons nothing, reboots nothing and
  injects no faults.
